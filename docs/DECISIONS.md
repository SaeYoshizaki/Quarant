# 設計判断の記録

新しい判断は末尾に追記する。覆すときは、元の項目を消さずに「Superseded by」を書く。

## D1 オフライン解析はキャプチャ時刻で動かす（2026-10-16）

- **判断**：時刻に関わる処理はすべてパケットの記録時刻で行う。対象は、イベントの時刻、フローの TTL、振る舞い検知の時間窓。
- **理由**：再現性と時系列比較が研究の前提だから。壁時計は、メタデータがないパケットの場合にだけ使う。

## D2 監視範囲を明示し、範囲外のホストを端末にしない（2026-10-16）

- **判断**：既定の監視範囲は RFC1918、リンクローカル、ULA とし、`--local-net` で変更できる。フローを持つ端末は、ローカル側の client を優先し、なければローカル側の server とする。
- **理由**：インターネット上のサーバーが端末一覧に入ると、新規端末通知を中心に誤検知が大量に出るから。

## D3 サーバー側の問題はサーバーに帰属させる（2026-10-16）

- **判断**：サービスの露出に関わる検出は、server がローカルなら server 側の端末に付ける。対象は I2 のサービス、HTTP 管理画面、LAN 内のサーバーへの平文リクエスト、Telnet。
- **理由**：リスクを持つのはサービスを公開している機器であり、接続したスマートフォンではないから。

## D4 根拠の種類を 3 値にする（2026-10-16）

- **判断**：`basis` は次の 3 値とする。
  - `observed`：検出のきっかけそのものが通信に現れていた。
  - `inferred`：ヒューリスティックや統計による判断。
  - `reference_match`：外部や知識 DB との照合。

  イベント型との対応は `analyzer/basis.go` で管理する。迷うものは `inferred` にする。
- **理由**：研究目的の「3 種類の情報を厳密に区別する」を、データ構造として保証するため。

## D5 CVE 候補は WARNING を上限とする（2026-10-16）

- **判断**：型番とファームウェアのバージョンが確認できない照合は `applicability=unconfirmed` とし、重大度は WARNING までにする。知識ベース側の重大度は evidence に残す。
- **理由**：「関連する CVE がある」と「脆弱である」は別のことだから（研究方針 5.8）。

## D6 振る舞い検知は説明可能な統計から始める（2026-10-16）

- **判断**：
  - スキャン：時間窓内の異なる宛先数と、未応答率で判定する。
  - 周期通信：間隔の中央値と、中央絶対偏差の比で判定する。
  - しきい値と測定値は evidence に書く。周期通信だけでは INFO とし、文脈フラグが 2 つ以上そろったら WARNING にする。
- **理由**：検証しやすく、誤検知の原因を追えるから。機械学習は Phase 3 以降に必要性を見て判断する。

## D7 脅威情報は一括取得してローカルで照合する（2026-10-16、Phase 2 で実装）

- **判断**：観測した IOC を 1 件ずつ外部に問い合わせない。
- **理由**：問い合わせそのものが利用者の通信を外部に漏らすから（データ取り扱い方針）。

## D8 知識ベースは go:embed で組み込む（2026-10-16）

- **判断**：`knowledge/*.json` と `knowledge/*.tsv` をバイナリに含める。`QUARANT_KNOWLEDGE_DIR` で差し替えられる。
- **理由**：カレントディレクトリに依存していたため、別の場所から実行すると失敗していたから。

## D9 正解ラベルつき合成シナリオで回帰を測る（2026-10-16）

- **判断**：`internal/synth` で生成した PCAP とラベルを、回帰テストと評価の基準にする。
- **注意**：検出器を知っている側が作ったデータなので、実環境での性能の根拠にはしない。実環境での評価には、実機または公開データセットが必要。

## D10 ルールは新しい情報があるパケットでだけ評価する（2026-10-17）

- **判断**：フローのバッファにも handshake の状態にも変化がないパケットでは、`rules.Run` を省く。
- **理由**：結果は変わらず、実 PCAP での処理時間が 53 秒から 7.6 秒になったから。
