## Phase 1：動作する基盤（PCAP → 根拠つきのセキュリティ情報）

**目的**：既存の PCAP から、時刻、帰属、根拠が正しいセキュリティ情報を安定して得る。教授に具体的な動作結果を示せる状態にする。

| 項目 | 状態 |
|---|---|
| キャプチャ時刻の使用、入力の終わりでのフローの確定 | ✅ |
| 監視範囲（`--local-net`）、外部 IP を端末として扱わない | ✅ |
| サーバー側の問題をサーバー側の機器に帰属させる | ✅ |
| 誤検知の修正（SYN のみ、管理画面、WebSocket、MQTT トピック、TLS フォールバック、CVE の重大度） | ✅ |
| 機器識別（MAC／OUI、DHCP、mDNS、SSDP、DNS） | ✅ |
| 振る舞い検知（スキャン、周期通信、IP と MAC の対応の変化） | ✅ |
| すべてのイベントへの `basis` 付与 | ✅ |
| 知識ベースの組み込み（実行ディレクトリに依存しない） | ✅ |
| ローカル API の CORS と DNS リバインディング対策 | ✅ |
| 外部ログの取り込みバグの修正（logread、Snort 3、Suricata、conntrack） | ✅ |
| 正解ラベルつき合成シナリオ、`label-eval`、機器レポート `devices` | ✅ |
| 実 IoT 機器の PCAP での検証 | ⬜（データの入手が必要） |
| 不要ファイルの整理、旧ツール `quarant-api`／`quarant-agg` の削除 | ✅ |

**完了条件**：

- `go test ./...` と `go vet ./...` が成功する。
- 合成シナリオで、観測可能な全ラベルを検出し、陰性対照での違反が 0 件。
- 実 PCAP を解析して、時刻、端末、帰属が正しい。
- `quarant devices` で機器ごとの説明ができる。

**検証方法**：`docs/TESTING.md` の手順、`quarant label-eval`、実 PCAP での目視確認。

## Phase 2：検出の拡張と、結果の統合

**目的**：既存ツールと外部情報を組み合わせて、検出できるリスクの種類を増やす。同時に、機器単位で根拠を保った統合を行う。

1. **相関エンジン**（研究の中核）
   - 独自エンジン、Suricata、Zeek、OpenWrt、脅威情報の検出を、機器 × 時間窓 × 宛先でまとめる。
   - 冗長なイベントを 1 つの「状況（situation）」にまとめる。合成シナリオでは 8 条件に対して WARNING 以上のイベントが 16 種類出ており、冗長性の定量化と削減の効果を測れる。
2. **SQLite ストレージ**：機器、イベント、フロー、識別の根拠、実行（run）を保存する。保存期間を設定でき、時系列で比較できるようにする（6.3）。
3. **脅威情報**
   - ThreatFox、URLhaus、Feodo などのフィードを一括取得してローカルで照合する。
   - 仕様、規約、レート制限は着手時に確認する。
   - IOC の鮮度を確信度に反映する。
4. **CVE**
   - NVD、CISA KEV、EPSS の取り込み。
   - 識別の確信度と、適用可否の 3 状態（確認済み／未確認／否定）を持たせる。
   - 知識ベースの出典を整備する（AUDIT 参照）。
5. **IoT プロトコル**
   - CoAP、RTSP、ONVIF、UPnP の詳細（SSDP の LOCATION 取得は能動的なので、パッシブで見えた範囲だけ扱う）。
   - NTP、DNS の異常（長いラベルやエントロピーによる DNS トンネリングの兆候）。
   - QUIC と UDP フロー。
6. **TLS**
   - JA4。
   - 1 レコード内の Certificate の解析、TCP 再組み立て（`tcpassembly`）。
   - TLS 1.3、ECH、QUIC で何が見えなくなるかを、可視性レポートに反映する。
7. **比較実験の基盤**：同じ PCAP を「Quarant 単体」「Zeek」「Suricata」「組み合わせ」で解析し、`label-eval` で比較するスクリプト。

**技術的な課題**：

- IDS とのアラート対応づけ（flow_id、5-tuple、時刻のずれ）。
- 脅威情報の誤検知（CDN の共有 IP）。
- SQLite スキーマの移行。

**依存関係**：

- 相関には `basis` と帰属（Phase 1）が必要。
- 時系列比較には SQLite が必要。

**完了条件**：

- 1 台の機器について、複数ソースの根拠を 1 つの状況として表示できる。
- 冗長性が下がる。
- 合成シナリオの再現率を維持する。

**検証方法**：

- 拡張した合成シナリオ（IDS で検出できる攻撃、IOC との一致を含める）。
- Suricata と Zeek を実際に動かした比較表。

## Phase 3：OpenWrt との連携と高度な解析

**目的**：実機ルーターでリアルタイムに監視し、通常時の振る舞いを学習して、そこからの逸脱を検出する。

1. **ハードウェア**：OpenWrt ルーターと解析ホスト（Pi 5 8GB 以上、または N100 クラスのミニPC）。ミラーまたは ssh ストリーミングで接続する。
2. **ライブ運用**：
   - 長時間の連続稼働（メモリの上限を設ける）。
   - 定期的な振る舞い評価。
   - パケット欠落の計測（pcap の統計）。
3. **ベースライン**
   - 機器ごとに、宛先の集合、時間帯別の通信量、プロトコル、周期を記録する。
   - まずは説明可能な統計（分位点、EWMA、新規宛先の出現）を使う。機械学習は必要になったら検討する。
4. **観測範囲の評価**：DHCP lease と観測の比較、Wi-Fi 内の通信の取りこぼしの定量化。
5. **緩和の実機評価**：既存の `mitigate` を、利用者の明示的な許可のもとで実機に適用し、before/after を比較する。

**完了条件**：

- 実機環境で 1 週間連続稼働する。
- ベースラインからの逸脱を、根拠つきで報告できる。
- 欠落率と観測範囲を数値で示せる。
