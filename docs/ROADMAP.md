# 開発ロードマップ

研究として使えるようにするための順序。研究の問いと評価計画は [RESEARCH.md](RESEARCH.md) を参照。前の段階が固まらないと、後の段階の結果が研究成果として通用しないため、この順に進める。

状態の凡例：✅ 完了　🔶 一部完了　⬜ 未着手

**完了条件**：

- `go test ./...` と `go vet ./...` が成功する。
- 合成シナリオで、観測可能な全ラベルを検出し、陰性対照での違反が 0 件。

- `quarant devices` で機器ごとの説明ができる。

**検証方法**：`docs/TESTING.md` の手順、`quarant label-eval`、実 PCAP での目視確認。

## Step 0：研究の問いと貢献の確定（最優先）

- **目的**：何を測れば「できた」と言えるかを決める。
- **作業**：
  - [RESEARCH.md](RESEARCH.md) の草案（研究の問い、想定する貢献、可観測性マトリクスの初版）について、教授と合意する。
  - 関連研究を一次資料で調べる（IoT Sentinel、IoT Inspector、Mon(IoT)r、YourThings など）。
- **完了条件**：研究の問いとスコープが確定し、RESEARCH.md の状態が「確定」になっている。
- **状況（2026-10-17）**：
  - 済み：問いの方向を合意した（ETSI EN 303 645 × 厳密にパッシブな可観測性、計測研究が中心）。COPSEC を含む関連研究を一次資料で確認した。RESEARCH.md、1 ページの要約（[RESEARCH-SUMMARY.md](RESEARCH-SUMMARY.md)）、README を書き直した。
  - 残り：教授との合意（SaeYoshizaki が担当）。

## Step 1：評価の土台を信頼できるものにする

- **目的**：これから出す数字が、研究成果として通用するようにする。
- **作業**：
  1. **既存ルールの精度監査**
     - UNSW の実データから、イベントの種類ごとにサンプルを取って正誤を判定し、適合率を出す。
     - 誤検知の多いルールは、修正するか、重大度と根拠の種類を見直す。
     - 既知の候補：`INSECURE_HTTP_BODY_SECRET`、`I9_DEFAULT_HOSTNAME_PATTERN`（接続先のホスト名で判定している）、I3／I4 のキーワード照合（`ota` の部分一致）、同じ弱い暗号について SELECTED と SUITE_OBSERVED の 2 件が出る問題。
  2. **カテゴリ推定の精度**：UNSW の機器一覧（31 台）と比べて正解率を出す。確信度の付け方を見直す（誤っているのに strong になる例がある）。
  3. **評価指標の定義**：検出を数える単位（イベント、条件、機器）、適合率と再現率の定義、開発用とホールドアウトの分け方を文書化する。
  4. **測定装置の妥当性検証（補助）**：差分ファジングを他のパーサ（HTTP、DHCP、MQTT）にも広げる。TCP の並べ替えと再送への頑健さも確かめる。
     - 済み：TLS（E2）。HTTP と MQTT、TCP の組み立て（E2b）。
     - DHCP は gopacket のデコーダを使っていて独自のパーサがないので、対象外とした。
  5. **再現できる実験の仕組み**：データの取得、解析、評価をスクリプトとして repo に置き（例：`scripts/experiments/`）、ハッシュ、コミット、設定を自動で記録する。
- **完了条件**：種類ごとの適合率の表がある。主要な誤検知を修正済み。E1 をスクリプト 1 本で再現できる。
- **状況（2026-10-17）**：
  - 済み：判定基準の土台として、ETSI TS 103 701 の全試験ケースのパッシブ評価可能性を分類した（E3、[assessment/](assessment/)）。
  - 済み：独立した 2 回目の分類と、食い違いの裁定。
  - 次：人による抜き取り確認。その後、E3 で不合格を示せるとした要件につながるルールから、精度監査に入る。

## Step 2：既存ツールとの比較（RQ3）

- **作業**：同じ PCAP を Zeek と Suricata（ET Open ルール）で解析し、取り込み機能を通して、同じ正解ラベルで評価する。
- **完了条件**：「Quarant だけが検出」「Suricata だけが検出」「両方が検出」の比較表がある。
- **判断**：フラッド系の検出器を自作するかどうかは、この結果を見て決める。既存ツールで十分なら、自作せず結果を取り込む。
- **状況（2026-10-17）**：
  - 済み：比較表を作った（[EXPERIMENTS.md](EXPERIMENTS.md) の S2、[assessment/tool-comparison.md](assessment/tool-comparison.md)）。
    - 取り込み機能は Zeek の notice を扱わないので、各ツールの出力を直接読む集計スクリプト（`scripts/step2/`）で比べた。
  - 分かったこと：
    - ARP スプーフィングは Quarant だけが検出した。反射攻撃（SSDP、SNMP）とマルウェアの種類は、Suricata だけが特定した。
    - フラッド系（TCP SYN、UDP、Ping、Smurf の 119 件）は、どのツールも検出しなかった。
  - 判断：フラッド系の検出器は今は作らない（D19）。研究の中心（ETSI の要件の可観測性）と直接つながらないため。
  - 残り：最近の機器のデータ（CIC IoT 2022）での比較。

## Step 3：Quarant 独自の価値を形にする（RQ1、RQ2、RQ4）

1. **相関エンジン**
   - イベントを、機器 × 時間窓 × 宛先・条件でまとめて「状況」にする。根拠はすべてたどれるようにする。
   - 測るもの：冗長性の削減と、まとめた後の再現率。
2. **可観測性マトリクスの実証**
   - RESEARCH.md §4 の各行を、データの根拠で裏づける。
   - 2016 年、2018 年、2022 年のデータを比べて、暗号化の影響を示す。CIC IoT 2022 の取得が必要。
3. **時系列比較とベースライン**
   - UNSW の 20 日分の連続データで、機器ごとの通常時の振る舞いと、そこからの逸脱を評価する。
   - SQLite でのデータ保存は、ここで入れる。
4. **脅威情報とのローカル照合**
   - 少量の C&C（Torii）への対策。
   - 当時の時点の IOC が手に入るかを、先に確認する。手に入らない場合は、現時点のデータで評価できる範囲に限ると明記する。

## Step 4：実環境での検証（ハードウェアの購入後、RQ5）

- **構成**：
  - OpenWrt ルーター
  - 解析用ホスト（Raspberry Pi 5、または N100 クラスのミニ PC）
  - 自分が所有する IoT 機器 2〜3 台
- **作業**：
  - 正解が分かる条件を意図的に作る（Telnet を有効にする、古いファームウェアを使う、など）。
  - リアルタイムで取得し、1 週間連続で稼働させる。
  - パケット欠落率と観測範囲（Wi-Fi 内部の通信を取りこぼしていないか）を測る。
  - 緩和策を、利用者の許可のもとで適用し、適用前後で評価する。
- **倫理**：自分の機器とネットワークに限る（RESEARCH.md §7）。
