# 見逃しの監査：Quarant と独立に作った正解との比較（E11）

精度を上げる手順 1（STATUS.md「最優先：論文の前に精度を上げる」）。E4〜E10 で確かめたのは正しさ（誤検出）だった。ここでは網羅性（見逃し）を測る。

## 方法

- **正解の作り方**：Quarant のコードを使わずに、元の PCAP から作った（[scripts/accuracy/](../../scripts/accuracy/)）。
  - **Zeek 9.0.0**（`gt.zeek`）：TLS、HTTP、MQTT、FTP を、ポートではなく中身で見つける（Zeek の DPD）。TCP を組み立ててから解析する。記録するのは名前だけで、値は記録しない（ヘッダ名、URL のパラメータ名、本文のキー名、Authorization の方式名、ユーザー名とパスワードの有無、本文の種類の推定）。
  - **生パケットの検索**（`rawscan.py`）：標準ライブラリだけで書いた PCAP の読み取りで、パケットごとに文字列を探す。HTTP 以外の独自プロトコルや UDP を補うために使う。暗号化された通信の途中には短い文字列（`pwd`、`sid`）が偶然現れるので、TLS のポートと Zeek が TLS と判断した通信は除いた。
  - tshark は、Homebrew の Lua の版の不整合で起動しなかったため使っていない。
- **比べ方**（`compare_misses.py`）：
  - 実行（日、回）ごとに、MAC で機器を特定した。IoT ではない機器は除外した（E4 と同じ除外リスト）。
  - Quarant 側は、E4 と同じ対応表（[evidence-map.json](evidence-map.json)）と同じ条件で数えた。
  - 正解だけにある機器は、次のどれにあたるかを自動で分けたうえで、1 台ずつ中身を確かめた。
    - **未対応づけ**：Quarant は検出しているが、その種類のイベントが対応表の要件に入っていない。
    - **帰属の違い**：Quarant は検出しているが、イベントを相手側の機器に付けている。
    - **未検出**：Quarant は何も出していない。
- **対象**：E10 の解析結果（`abf5d92`、全 1,084 件）。UNSW 2016（20 日）、UNSW 2018（攻撃データ 6 日）、IoT-23（8 シナリオ）、CIC IoT 2022（起動時、待機時、操作時、生活場面、日中、RTSP の攻撃）。
- **判定**：名前の一致は候補にすぎないので、正解側の候補もすべて中身を確かめた。判定は Claude 1 人。値は伏せ、キー名と文脈（メソッド、ポート、プロトコル）だけで判断した。
  - 1 回だけ、文脈の表示の範囲が値の途中から始まり、値の一部が会話に表示された（Luohe のカメラ）。ファイルには残していない。以後は、区切りの前を捨て、`=` の後ろを `***` に置き換えて表示した。
  - 判定は [miss-judgments.json](miss-judgments.json) に残した。`compare_misses.py` に渡すと、判定済みの集計を出す。判定のない候補は unjudged と表示されるので、測り直しで新しい候補が出たら判定を足す。

## 見逃しの一覧と原因

| 要件 | 機器（データ） | 種類 | 観測された事実 | 原因 |
|---|---|---|---|---|
| 5.5-1 | Insteon のカメラ（UNSW 2016、1 日） | 帰属の違い | カメラが **TLS のサーバー**で、スマートフォンが TLS 1.2 を提示したのに TLS 1.0 を選んだ（LAN 内、443 番） | Quarant はイベントを接続元（スマートフォン、除外対象）に付ける。古い版を選んだのはサーバー側の機器 |
| 5.5-1 | Blipcare の血圧計（UNSW 2016、3 日） | 未検出 | 8777 番ポートの外部サーバーとの TLS で、サーバーが TLS 1.0 を選んだ | 機器が TLS のレコードヘッダ（5 バイト）だけを最初のパケットで送る。Quarant の中身による TLS の判定（`looksLikeTLSRecord`）は最初のパケットに 6 バイト以上を求めるので、既定外のポートでは TLS と認識しない |
| 5.5-6 | Withings の機器 4 台（ベビーモニター 2、体重計、睡眠センサー。UNSW 2016） | 未対応づけ | HTTP の POST の本文に `sessionid`、`auth` を入れて withings.net へ送る。応答にも `sessionid` | Quarant は `INSECURE_HTTP_BODY_SECRET` で検出しているが、この種類が 5.5-6 に対応づけられていない |
| 5.5-6 | iHome（UNSW 2016） | 未対応づけ | LAN 内の HTTP の本文に `evrythng.api_key` | 同上 |
| 5.5-6 | Insteon のカメラ（UNSW 2016） | 未検出 | スマートフォンのアプリが、34100 番ポートの HTTP で、URL にユーザー名とパスワードを入れてカメラにログインする（LAN 内）。カメラの応答にもパスワードのキーがある | LAN 内の既定外ポートの HTTP は、既存の検出にかけない（D17、既知の問題 8） |
| 5.5-6（5.5-7） | Luohe のカメラ（CIC 2022 の操作時、3 回） | 未検出 | **外部（WAN 側のアプリ）から UDP の P2P 通信で、`user=`、`pwd=` 形式のログイン情報が平文で届く** | Quarant は UDP の中身を解析しない |
| 5.8-1 | TP-Link Day Night Cloud カメラ（UNSW 2016、2 日） | 未検出 | tplinkcloud.com の中継サーバーへ、HTTP の POST（multipart）で **h264 の映像と AAC の音声**を平文で送る | multipart の本文で、最初の部分の Content-Type だけを見ている。このカメラは最初の部分が `text/plain` で、映像と音声は 2 番目以降 |
| 5.8-1 | Borun のカメラ（CIC 2022 の起動時、3 回中 2 回） | 未検出 | HTTP ではない独自のバイナリプロトコルで、8899 番ポートの外部サーバーへ JPEG を暗号化せずに送る（パケットの 8 バイト目から JPEG の署名） | Quarant はメディアを HTTP の中でしか探さない |

## 正解の候補から外したもの（秘密情報ではない）

| 候補 | 理由 |
|---|---|
| UPnP の `SID:` ヘッダ（Belkin など） | UPnP のイベント購読（GENA）の識別子 |
| Belkin の本文の `…pwd…` を含む長いキー | ランダムな文字列にたまたま `pwd` が含まれていた |
| `sign`（Tuya、closeli、av380 など）、`signature` | 要求ごとの署名。使い回せる秘密ではない |
| Authorization の `OSS`（Home Eye）、`AWS4-HMAC-SHA256`（SimCam）、`Digest`、`WSSE`（Amcrest） | 要求ごとの署名・ダイジェスト。E9 の判断（AWS SigV4 は除外）と同じ扱い |
| Philips Hue の応答の `unauthorized` | キー名に `auth` を含むだけ |
| Sonos の `sonosid`、`householdid` | 識別子（E4 の判断と同じ） |
| 暗号化された通信や、ファームウェアなどのバイナリの中の `pwd`、`sid` | 偶然の一致 |
| Philips Hue（UNSW 2018）の本文が音声と推定されたもの | Zeek の推定の誤り。720 バイトの API の本文で、Hue にはマイクがない |
| CIC の RTSP の攻撃データの認証情報 | 攻撃者（Hydra）の推測。機器自身の秘密情報ではない。また Zeek が RTSP を HTTP として解析していた |

## 判断を保留したもの

- **セッション ID らしいパラメータ**：Amazon の機器（UNSW 2016）の `sid=`、Sonos の `sid=`（E8 と同じ）と `AISSessionId` の Cookie（ラジオ配信サーバーから）。何のセッションかが分からない。Quarant は前の 2 つを 5.5-6 として数えている。
- **HP のプリンタ**の Cookie と `X-Privet-Token`（LAN 内）。プリンタの管理画面のセッションと、ローカル API の偽造防止用のトークン。両方が検出していて、ここでは正解に入れた。

## 見逃し以外に見つかったこと

1. **誤検出（5.5-6）**：Home Eye のカメラの `Authorization` ヘッダは、Alibaba Cloud OSS の要求ごとの署名だった。AWS SigV4 と同じく使い回せる秘密ではないが、Quarant は方式名を残さない（`Authorization: ***`）ため、除外できずに 5.5-6 として数えている（CIC の起動時、待機時、日中の各 1 台）。
2. **IoT ではない機器の混入（E4 の数字に影響）**：UNSW 2018 には機器の一覧がなく、除外リストは 2016 年の一覧から作っていた。そのため、攻撃用の `kali`、HP Compaq の PC 2 台、MacBook Pro が、IoT 機器として数えられていた（32 台のうち 4 台）。
   - **E4 の UNSW 2018 の 5.8-1（1 台、3%）は、MacBook Pro だった。** IoT 機器に限ると 0 台になる。5.3-4A、5.8-2、6-8 にも、この PC が入っている。
3. **既定外のポートの外部への HTTP**（既知の問題 8）：Belkin の機器（8899 番への PUT）、Belkin NetCam（8899）、av380 のカメラ（8002 への POST）、Sonos（9322）。どれも、正解側でも秘密情報やメディアは見つからなかった。この範囲での見逃しは、今回のデータでは 0 件だった。

## 限界

- **正解の作り方も名前に頼っている**：秘密情報の正解は、キー名やヘッダ名の一致で候補を作った。秘密らしい名前の付いていない値（独自のバイナリ形式の中の鍵など）は、正解にも Quarant にも現れない。Quarant と同じ考え方の検出なので、両方が同じものを見逃している可能性がある。
- **生パケットの検索はパケット単位**：複数のパケットにまたがる文字列は見つからない。主な正解は Zeek（組み立てたあとの解析）で、生パケットの検索は補助として使った。
- **TLS の正解は Zeek に依存する**：S2 では、Zeek と Suricata のログが同じ機器を記録していた。Zeek が TLS と判断できない通信は、正解にも入らない。
- **判定は 1 人（Claude）**：手順 4 で、利用者による抜き取り確認を行う。
- **値を確かめていない**：たとえば、Withings の `sessionid` が本当に有効なセッションかは確かめていない（値を見ないため）。

## 測り直し（E12）

修正（`3ae8b2c`、D23）のあとに、同じ正解と判定で測り直した。上の一覧の見逃し 11 件は、すべて Quarant が検出するようになった。Home Eye の OSS の署名は、5.5-6 に数えなくなった。詳細は EXPERIMENTS.md の E12。

```bash
python3 scripts/accuracy/compare_misses.py docs/assessment/evidence-map.json ~/datasets/runs-fix ~/datasets/gt-e10 docs/assessment/non-iot-macs.txt <out.json> docs/assessment/miss-judgments.json
```
