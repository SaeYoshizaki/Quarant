# 精度監査：違反の証拠として使う Quarant の検出（E4）

## 目的と方法

- **目的**：E3 で「違反だけ示せる」とした要件について、対応する Quarant の検出が、その要件の違反の証拠として正しいかを確かめる（[evidence-map.json](evidence-map.json)）。
- **方法**：
  - 公開データ（UNSW 2016、11 日分）の解析結果から、検出の種類ごとに最大 15 件を無作為に抜き出した（乱数の種は 20261017）。
  - Claude が、イベントの根拠（evidence）、送信元と宛先、機器を読み、正誤を判定した。
  - 判定は「その要件の違反を示すか」で行い、「検出したもの自体があるか」では判定していない。
- **限界**：
  - 抜き取りは小規模。データセットも UNSW 2016 が中心。
  - 判定は 1 人（Claude）で、人による確認はしていない。

## 主な所見

1. **プロトコルが公開を義務づけている情報（5.6-2）**：一見「情報漏れ」に見えるもっとも目立つ証拠、つまり機器が自分から流すバージョン文字列は、ほとんどが規格上の違反ではなかった。
   - UPnP の SERVER ヘッダ（`Linux/2.6.21, UPnP/1.0, Portable SDK for UPnP devices/1.6.6` など）は、プロトコルの仕様で書くことが求められている。
   - mDNS の `pv=1.0` や `vers=2.5` は、ソフトウェアのバージョンではなくプロトコルのバージョンだった。
   - TS 103 701 の 5.6-2 も、標準プロトコルが求める公開は製造者が最小化できないと注記している。
2. **検出の名前と要件の意味のずれ**：同じ検出（INSECURE_HTTP_AUTH）が、ある要件（5.5-6）では正しい証拠で、別の要件（5.1-2A）では誤った証拠になる。要件との対応づけには、根拠の中身による絞り込みが要る。
3. **イベントの向きの不具合**：サーバーからの応答で検出したイベントでは、送信元と宛先が逆になっていた。Quarant 本体を直し、検出は常にクライアントからサーバーへの向きで記録するようにした（テストあり）。
4. **既知の問題**：シリアル番号などの識別子が INSECURE_HTTP_TOKEN（トークンの平文送信）として出力される。名前と中身が合っていない（STATUS.md の既知の問題に記載）。

## 追加の確認：IoT-23 だけに現れた証拠

- **5.5-6／5.5-7**：Philips Hue（ハニーポット 4-1）が、クラウド（ポート 80）へ `Authorization` ヘッダと `auth=` の URL パラメータを平文で送っていた。機密情報の平文送信として正しい。
- **5.9-3**：大半が無応答の再接続ループ 3 件（シナリオ 3-1、34-1、8-1）は、マルウェアの C2 やスキャンの繰り返しだった。製品の再接続の設計ではなく、感染による振る舞いである。通信だけでは、この 2 つを区別できない。そのため候補止まりのままにする。
