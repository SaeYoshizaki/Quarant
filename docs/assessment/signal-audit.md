# パッシブな手がかりの棚卸し（C2、UNSW 2016 の開発用 10 日）

機器のカテゴリを決める手がかりが、それぞれの機器の通信に**そもそも含まれているか**を調べた。推定の規則の良し悪しではなく、パッシブな観測で届きうる範囲を知るのが目的。

- **データ**：UNSW 2016 の開発用の 10 日（16-09-23〜16-10-02）。評価用の 10 日は見ていない（D11）。
- **名乗りと DHCP**：C1b の版（`bda0e71`）で解析した各日の `device_inventory.json` の `identity_evidence`。
- **通信の形**：`scripts/assessment/trafficshape`（ヘッダだけを読む）を、各日の PCAP にかけた。
- **集計**：`scripts/assessment/signal_audit.py`。下の段階分けは、その出力を見て手で判定した。
- **正解**：[unsw-categories.json](unsw-categories.json)（Claude が付けた。人による確認はまだ）。

## 段階の定義

| 段階 | 機器が出しているもの | カテゴリを決めるのに必要なもの |
|---|---|---|
| A | カテゴリそのものを名乗る（プロトコルが定める種類、一般的な語） | 名乗りの読み取りだけ（`observed`） |
| B | 製品名や型番だけを名乗る | 製品の知識（`reference_match`） |
| C | 名乗りがない。ベンダー（OUI、DHCP の vendor class、DNS）とプロトコルだけ | 通信の形やプロトコルからの推定（`inferred`） |

## 分かったこと

### 1. 名乗りがあるのに使えていない分がある（段階 A の取りこぼし）

- **日ごとに独立して解析しているため、名乗りが失われる。** mDNS の告知や DHCP の要求は、機器の起動時や更新時にしか出ない。SmartCam の `_rtsp._tcp` は 4/10 日、iHome の `ci=7` は 1/5 日、TP-Link カメラの mDNS は 4/10 日にしか見えなかった。連続して動く監視なら、一度見た名乗りを MAC アドレスごとに覚えておける。
- **同じ機器が IP アドレスごとに別の機器として扱われる。** プロファイルが IP アドレスごとに作られるため、SmartCam は同じ日に IPv4、IPv6 のリンクローカル、169.254.x の 3 つに分かれた。名乗りもこれらに分散する（16-09-28 は、IPv6 の側では Camera/high、IPv4 の側では Camera/medium）。C1 と C1b の評価は、機器と日ごとに最初の行だけを数えていた。
- **規則が知らない種類名がある。** Wemo スイッチの `controllee`（Belkin が定めた UPnP の機器の種類）。

### 2. 製品名だけを名乗る機器は、製品の知識があれば決まる（段階 B）

- 5 台はどれも、毎日のように製品名や型番を名乗っている。カテゴリを決めるには、製品名からカテゴリへの対応表が要る（`reference_match`）。
- 対応表は、このデータの機器に合わせて作ると過学習になる。データセットとは別の出典（各社の製品一覧など）から作り、評価用のデータで確かめる必要がある。

### 3. 名乗りがない機器にも、通信の形やプロトコルに手がかりがある（段階 C）

- **はっきりしているもの**
  - **常時アップロード**：Dropcam。ほかのどの IoT 機器にもない形。
  - **映像配信のプロトコル**：ベビーモニターの RTMP。SmartCam の RTSP も同じ種類の手がかり。
  - **1 日に数分しか通信しない**：NEST Protect、体重計、血圧計。3 台とも Sensor（または Wearable）。電池で動く機器の特徴と考えられる。
- **区別が難しいもの**：Echo、Insteon、SmartThings、待機中のカメラ（TP-Link、ベビーモニター、SmartCam の WAN 側）。どれも接続を保ち、上りは毎分数百バイト〜2 KB 程度（中央値）しかない。この形はプラグや Hub と同じで、**通信量だけでは区別できない**。待機中のカメラは、動きを検知したときしか映像を送らないためと考えられる。これが、パッシブで分かることの限界の 1 つの候補。

### 4. IoT ではない機器は、通信の形で分けやすい

- スマートフォンと PC（観測された 6 台）は、問い合わせる DNS 名が 40〜614 個ある（観測した全日の合計。1 日しか観測していない機器でも 44 個以上）。IoT 機器は、10 日の合計でも多くて 22 個。
- 上りの比率も、スマートフォンと PC は 0.05〜0.41 と小さい。IoT 機器はほぼ 0.45 以上。例外はフォトフレーム（0.24、画像をダウンロードする機器）。

## 限界

- 1 つの家、19 台、10 日だけの観察。通信の形についての所見は傾向にすぎない。初めて見る機器に通用するかは、ROADMAP の次の段階（機器ごとに学習から外して評価する上限の実験）で確かめる。
- 段階の判定は手で行った。名乗りが「カテゴリそのもの」か「製品名」かの境目には判断が入る（例：TP-Link カメラの「Little Cam」は、利用者が付けた名前と思われる）。
- `trafficshape` の接続の単位は 5 つ組（プロトコル、相手の IP、両方のポート）。送信元ポートを固定して使い回す機器（体重計）では、短い接続が 1 本の長い接続に見える。
- 正解のラベルは、人による確認がまだ。
