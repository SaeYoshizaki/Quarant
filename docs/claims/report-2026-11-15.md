# 公式文書と通信の食い違い：報告（2026-11-15）

公開の IoT データセット 7 つで、製造者の公式文書の説明と、実際の通信が合わないものを探した。この文書は、そのうち強い候補をまとめた報告である。候補ごとに、根拠の通信、公式文書の原文、似た資料（論文・ブログ）、別の読み、確かめていないことを並べる。

- 「食い違いの候補」は、文書の言葉と通信が合わないという意味で、製造者の誤りや違反を断定するものではない。
- 通信はすべてパッシブに見た（機器への操作、TLS の復号はしていない）。
- 文書は収録の時期に公開されていた版を Wayback Machine で読んだ。収録の前（before）、収録中（during）、収録の後（after）を書く。
- 先行研究は「同じ食い違いを示したもの」と「通信の問題そのものを示したもの」を分けて探した。見つからないことは、新しいことの証明にはならない。
- **訂正**：これまでの記録では、Samsung の 2 機種（A、D）でもサーバーがすべての接続で AES-128 を選んだとしていた。この報告を書くために確かめ直したところ、XMPP の接続（STARTTLS のあとの TLS）を洗い出しが読めておらず、そこではサーバーが AES-256 を選んでいた（[C 節](#c-aes-256と書いた製品サーバーが-aes-128-を選ぶ)）。記録は直した。
- 詳しい記録：[sweep-results.md](sweep-results.md)（「根拠の補強」の節）、[review-sweep.md](review-sweep.md)（1 行ずつ確かめる表）、[claims.tsv](claims.tsv)、[sweep/prior-claims.tsv](sweep/prior-claims.tsv)、[longitudinal.md](longitudinal.md)。

## 1. 方法

- **データ**：UNSW 2016（Sivanathan ほか）、UNSW-IoTraffic（2016-09〜2017-04）、YourThings 2018（Alrawi ほか, IEEE S&P 2019）、UNSW 2018（SOSR 2019 のデータの正常な日、MIT-0）、IoT-23 の正常な 3 シナリオ（Garcia ほか 2020, doi:10.5281/zenodo.4743746, CC BY 4.0）、CIC IoT 2022（Dadkhah ほか, PST 2022）、Deakin IoT Traffic 2023-24（Pasquini ほか 2024）。出典と条件は [DATASETS.md](../DATASETS.md)。
- **通信**：`scripts/claims/sweep/` で PCAP を 1 回読み、平文の識別子、TLS の版と暗号などを製品ごとにまとめた。候補は tshark で開き直して確かめた（ファイル名とフレーム番号を書く）。
- **文書**：製品ページ、仕様、マニュアル、FAQ、プライバシーポリシーを Wayback Machine から集め、引用は保存した本文と機械で照合した（`scripts/claims/check_quotes.py`）。
- **機種**：機器が LAN で名乗った情報（UPnP、mDNS、DHCP）から機種を確かめた（`scripts/claims/sweep/lan_models.py`）。文書がその機器に当てはまるかを決めるため。
- **先行研究の区分**：4 会議（IEEE S&P、USENIX Security、ACM CCS、NDSS）の論文が同じ機器の同じ問題を詳しく示していれば外す。ほかは「論文で一部」「ブログ等のみ」「見つからず」。

## 2. 強い候補

### A. Samsung SmartCam SNH-P6410BN（UNSW 2018）：ライブ映像と音声が平文

**機器と機種**

- MAC 00:16:6c:ab:6b:88、IP 192.168.1.248。UNSW 2016、UNSW-IoTraffic、UNSW 2018 に同じ個体がいる。
- 機器自身の UPnP の説明に `modelName` SNH-P6410BN、`serialNumber` KHNL6V2H20003LX（UNSW-IoTraffic `BelkinCamera_b4750eece5a9.pcap` フレーム 26、2017-02-21。UNSW 2018 `18-05-28.pcap` でも 1,098 回、同じ値）。

**根拠の通信**（UNSW 2018 `18-05-28.pcap`）

- 外の相手 129.94.5.83 から、カメラの tcp/40000 への接続が 20 回（各 15〜20 秒）。
- そのうち相手のポートが 48041 の 1 回（フレーム 3194834〜3201825、2018-05-28 15:43:35〜15:43:52 UTC、約 5.1 MB）を組み立て直した（`tshark -z follow,tcp,raw`）。RFC 4571 の 2 バイトの長さの後に、STUN が 25 個と RTP が 3,953 個。
  - RTP の PT 97 は H.264（High、1920×1080、471 フレーム）、PT 0 は G.711 μ-law の音声（15.8 秒）。
  - 暗号化はなく、**映像は絵として、音声は音としてそのまま再生できた**（実験室の机の上が写っている）。
- 送り先：STUN サーバー（13.56.104.1）が返したカメラの外側のアドレスは 149.171.37.10（フレーム 815596 の XOR-MAPPED-ADDRESS）で、視聴者の 129.94.5.83 とは別。ICE の確認は視聴者の私設アドレス 192.168.111.239 にも出ている（フレーム 815712 ほか）。映像は**実験室の LAN の外にいる視聴者**へ送られていた（視聴者が誰かは未確認）。
- クラウドとの TLS はどれも TLS 1.0。カメラは 49 種類の暗号を出し、1 番目は AES-256（ECDHE_RSA_AES256_SHA）、AES-128 は 26 番目。
  - HTTPS（tcp/443）のサーバーは `TLS_ECDHE_RSA_WITH_AES_128_CBC_SHA` を選んだ（2018-05-28 に 10 回。例 フレーム 1139891/1139906）。
  - XMPP（tcp/5222、STARTTLS のあとの TLS。直前の DNS の応答（フレーム 1139722）で xmpp.samsungsmartcam.com）のサーバーは `TLS_ECDHE_RSA_WITH_AES_256_CBC_SHA` を選んだ（同じ日に 10 回。例 フレーム 1139786/1139793）。
- 取り出した映像・画像・音声は公開のリポジトリに入れず、`~/datasets/claims/dig/smartcam/` に置いた（人や実験室が写っているため）。

**似た資料**

- Kaspersky ICS CERT（Muravitsky, Dashchenko, 2018-03-12, https://securelist.com/somebodys-watching-when-cameras-are-more-than-just-smart/84309/）：SNH-V6410PN（別の機種）で、ファームウェアの更新と HTTP API に安全でない HTTP を使うと指摘。ライブ映像の運び方と暗号化には触れていない。Kaspersky Daily（2018-03-16）は「intercept the video stream, tap the audio channel」とするが、経路は書いていない。
- CVE-2018-6295（NVD, 2018-03-13）：「Unencrypted way of remote control and communications」。どの通信かは書いていない。
- Loi ほか（IoT S&P Workshop at ACM CCS 2017, Table 1 p.3）：同じ研究室の SmartCam の機器とサーバーの通信は平文ではない（エントロピー 7.99）。機器とアプリの間は調べていない。こちらの観測とは逆。
- Wannigama ほか（IEEE WoWMoM 2024, arXiv:2404.07408, §II-A p.2-3）：同じ UNSW の 2016 年の通信で、TLS 1.0 とサーバーが選んだ 0xc013（AES-128）を報告。映像や RTP は扱っていない。
- 別の会社のカメラの平文の映像：TP-Link（Loi ほか 2017）、Ring（Alharbi & Aspinall 2018）。
- **区分**：食い違いは見つからず。平文の映像そのものは、SmartCam については見つからず（近いのは Kaspersky のブログだけ）。

**別の読みと弱い点**

- 平文の映像は、利用者が「Image encrypting」を入れていなかったことで説明できてしまう。強く言えるのは次の 2 点。
  - 仕様の「SSL (AES 256bit)」は条件なしに書かれているのに、映像は初期のままでは暗号化されない（画面の写真では初期値がオフ）。
  - クラウドとの TLS は TLS 1.0 で、HTTPS の接続は AES-128 だった（サーバーの選択）。XMPP の接続は AES-256 で、こちらは仕様と合う。
- 視聴者は UNSW の中のアドレスで、映像が大学の外のインターネットを通ったかは分からない。

**未確認**：Image encrypting の初期値、ファームウェアの版、「SSL」がどの通信を指すか、2024 年のマニュアルが 2016 年のファイルと同じか。

### B. SimCam 1S（CIC IoT 2022）：人が写った画像を平文でクラウドへ

**機器と機種**

- CIC の「SimCam」、MAC 10:2c:6b:1b:43:be。機種は SIMCAM 1S（Kostas ほか, arXiv:2307.08679 の表による。機器の名乗りでは確かめていない）。製造元は Simshine。

**根拠の通信**（CIC `2021_11_02_Active.pcap`）

- カメラ（192.168.137.149）から平文の HTTP の PUT が 15 回（フレーム 1234、31182、49493、55439、63508、159940、162589、191121、196541、230237、475243、498331、617912、623193、631073）。宛先は `elasticbeanstalk-us-east-2-793503604989.s3.amazonaws.com:80/SimCam/{id}/PersonDetect/{id}`（AWS4 の署名つき。キー ID は非公開のリポジトリ quarant-results）。
- 中身（`tshark --export-objects http`）：15 個すべてが JPEG（480×270、22〜25 KB）として開け、**15 枚すべてに人が写っている**（暗い室内、赤外線の白黒）。
- 順番：`www.luuka.fun:80/event/event/saveEvents` の約 0.3〜0.4 秒後に PUT、その約 0.2〜0.3 秒後に `/push/push/pushMessage`（例：フレーム 1093 → 1234 → 1293、2021-11-02 11:15:12.9〜13.5 UTC）。saveEvents は 16 回あり、PUT のない 1 回（フレーム 68761）は 20 秒後に通知だけが出ている。通知に付ける画像だと推定する（推定。イベントと通知の本文は base64 の暗号文で読めない）。
- CIC のどのキャプチャでも、このカメラの TLS の握手は 1 回もない（公開のアドレスへの 57 MB）。
- 1 時間に 1 回、`ipinfo.io`、`myip.ipip.net`、`icanhazip.com`、`ip.cip.cc` に平文の HTTP で自分の公開アドレスを問い合わせている。

### C. 「AES 256」と書いた製品：サーバーが AES-128 を選ぶ

機器が最初に出した暗号と、製造者のサーバーが選んだ暗号を比べた。どの製品も、機器は AES-256 を先に出し、サーバーが AES-128 を選んでいた。ただし Samsung の 2 機種では、XMPP のサーバーは AES-256 を選んでいて、AES-128 は HTTPS の接続だけだった。

| 製品（データ） | 文書の言葉（版、収録との関係） | 機器の提示（ClientHello） | サーバーが選んだもの |
|---|---|---|---|
| Awair（UNSW-IoTraffic） | 「Awair encrypts and stores all information over TLS (Transport Layer Security) and AES 256 bit encryption to ensure security.」（サポートの FAQ、[2016-07-31](https://web.archive.org/web/20160731193440/http://support.getawair.com:80/hc/en-us/articles/206241477-How-secure-is-Awair-)、before。2019-08-23 の版にも同じ文） | `AwairAirQuality_70886b100fc6.pcap` フレーム 22。DHE_RSA_AES256_SHA256 が 1 番目（17 種類） | TLS_RSA_WITH_AES_128_CBC_SHA256（744/826。前方秘匿性もない） |

**Samsung の 2 機種について（訂正）**

- Samsung のカメラは、遠隔操作の XMPP（tcp/5222）で、平文の XMPP を始めてから STARTTLS で TLS に切り替える。洗い出し（`scripts/claims/sweep/expose.py`）は接続の先頭が TLS のときだけ握手を読むので、この握手を数えていなかった。
- tshark で数え直した結果：
  - SNH-P6410BN（UNSW 2018）：2018-05-28 に XMPP 10/10 が AES-256、HTTPS 10/10 が AES-128。ほかの日は数えていない。
  - SNH-P6410BN（UNSW-IoTraffic）：XMPP 89 回のうち 84 回が AES-256（TLS_ECDHE_RSA_WITH_AES_256_CBC_SHA）、**5 回が 3DES（TLS_ECDHE_RSA_WITH_3DES_EDE_CBC_SHA）**（`SamsungCamera_00166cab6b88.pcap` フレーム 147222〜1173960）。HTTPS 65 回は AES-128。
  - SNH-V6410PN（Deakin）：新しい接続のある 7 日で XMPP 17/17 が AES-256-GCM。HTTPS 16/16 は AES-128-GCM。
- つまり「SSL (AES 256bit)」は XMPP の接続には合う。合わないのは、HTTPS の AES-128、平文の HTTP（イベントの通知）、平文の映像（A）、IoTraffic の 3DES の 5 回。
- 「サーバーが AES-128 を選ぶ」がすべての接続で言えるのは、Awair、iRobot、Somfy、Withings Home の 4 製品。
- 洗い出しの全体で STARTTLS で始まる接続は、Samsung のカメラのほかに Withings Aura（2 本）と HP ENVY（1 本）だけだった。

**対照**

- Canary は「AES 256-bit data encryption」（[canary.is/canary 2016-12-19](https://web.archive.org/web/20161219082400/https://canary.is/canary/)）と書き、サーバーは AES-256-GCM を選んでいた（UNSW-IoTraffic 5,831/5,843、UNSW 2018 41,035/41,075）。
- Nest Cam は「128-bit AES encryption with TLS/SSL」（Google Store カナダ、[2021-10-20](https://web.archive.org/web/20211020173952/https://store.google.com/ca/product/nest_cam_indoor_specs?hl=en-CA&GoogleNest)）と書き、実際も AES-128 だった（ただし TLS 1.0。[3 節](#3-ほかの候補弱いもの)）。
- 書いてある鍵の長さが正しい製造者もいるので、「AES 256」の誤りはどこでも起きる表記の揺れではない。

**似た資料**

- Paracha ほか、IoTLS（ACM IMC 2021, doi:10.1145/3487552.3487830）§1 p.166、§5.1 p.172 と Fig.3、§6 p.173：機器は前方秘匿性に対応しているのに、サーバーの対応がなくて弱い接続になる、という集計。AES の鍵の長さは扱っていない。6 製品はどれも機器の一覧にない。
- Wannigama ほか（IEEE WoWMoM 2024, arXiv:2404.07408v1, §II-A p.2-3、注 2〜3）：UNSW 2016 の通信で、Awair、Samsung のカメラなどのサーバーが「consistently chose a weak code from the client-suggested ciphersuite」。注 3 は Ring で、AES-256 を先に出したのに AES-128 が選ばれた例。製造者の説明とは比べていない。
- AV-TEST（E. Clausing, 2017-01-06）：Withings Home の画面の写真に、同じ暗号（ECDHE_RSA_AES_128_GCM）の Server Hello が写っている。「sufficiently secure」とする。
- Alrawi ほか（IEEE S&P 2019, Table V p.17）：サーバー側の TLS を能動的に調べた結果だけで、暗号の選択の比較はない。
- 読めなかったもの（未確認）：IoTLS 2.0（EuroSec 2026）の本文、Akgul ほか（WPES 2021）の本文。
- **区分**：「AES 256」の説明と、サーバーが選んだ暗号を比べた資料は、どの製造者についても見つからず。サーバーが機器より弱い方を選ぶこと自体は、論文で一部知られている（4 会議の論文ではない）。

**別の読みと弱い点**

- AES-128 自体は弱くない。問題は説明が正確でないこと。弱さとして意味があるのは、前方秘匿性のない RSA 鍵交換をサーバーが選んだ Awair と Somfy。
- Awair と Withings の文は、保存時の暗号化（AES 256）を言っているとも読める。Somfy の文は、どの接続のことか書いていない（錠の単体のページでは Bluetooth の話）。
- Awair の UNSW 2018 では AES-256 が 1,116 回中 705 回で、AES-128 は 353 回（32%）。

## 4. 年をまたいで見る

2 つ以上のデータセットにある 32 製品を [longitudinal.md](longitudinal.md) に並べた。同じ MAC（同じ個体）で読めること：

- 平文が減った：Amazon Echo 80% → 62% → 3%（2016 → 2018）、TP-Link NC220 92% → 11% → 0.3%。
- 平文が続いた：Hue（E）。
- 平文が増えた：Invoxia Triby 10% → 62% → 72%。
- TLS 1.0 が続いた：Belkin WeMo Motion、LIFX、TP-Link HS110、Samsung SmartCam、Dropcam（2016〜2018）。Nest Cam は 2021 年でも TLS 1.0 だけ。
- 文書の版と並べて、「説明と通信のどちらが先に変わったか」を見ることは、まだしていない。

## 5. 機種の特定

データセットの機器名は「Samsung SmartCam」のように大まかで、文書がその機器に当てはまるかを決められないことがあった。機器が LAN で名乗った情報を読むスクリプト（`scripts/claims/sweep/lan_models.py`）で、7 製品・16 台の機種を確かめた（[devices.tsv](devices.tsv) の model_basis に根拠）。

- これで SmartCam の機種が SNH-P6410BN と分かり、それまで比べていた仕様の表（SNH-C6417BN、SNH-V6414BN）が別の機種のものだと分かった。
- 機種が分からないまま：Roomba（`iRobot-<BLID>` だけ）、Somfy（`ESP_1E7654`）、Gosund と Globe、Amcrest、Canary。

## 6. 研究としての位置づけ（案）

- いちばん近い先行研究は Subahi & Theodorakopoulos（IEEE FiCloud 2018）で、IoT 機器のプライバシーポリシーと自前のテストベッドの通信を比べている。セキュリティの主張は扱っていない。
- 宣言と挙動を比べる研究はモバイルのアプリにある（PoliCheck, USENIX Security 2020、Koch ほか, PoPETs 2022）。どれも能動的。
- 見つからなかったもの：IoT 機器のセキュリティの主張（暗号化など）を通信と比べた研究、公開データセットを後から読み直して当時の文書と比べた研究。
- 新しさになりそうな点：
  1. 「AES 256」と書いた 4 社の製品で、食い違いが機器ではなくサーバーの設定から来ていること（C。Samsung は HTTPS の接続だけ）。対照（Canary、Nest Cam）もある。
  2. 「暗号化」「ローカル処理」をうたうカメラが、映像や人の画像を平文で送っていたこと（A、B）。
  3. 同じ製品を 2016〜2024 年のデータで追い、問題が続くか、直ったかを見たこと（D、E、4 節）。
  4. 機器の名乗りから機種を自動で決め、当てはまる文書を選べること（5 節）。

詳しくは [related-work.md](related-work.md)。

## 8. 判断が要ること

1. **SmartCam の平文の映像の数え方**：食い違いとして数えるか、「初期のままでは映像が暗号化されない」問題として別に数えるか。別の機種の仕様の行（[review-sweep.md](review-sweep.md) の 17〜20）を外すか。
2. **SimCam の文書の範囲**：App Store の説明と中国語のポリシーを、比べる文書に含めるか。
3. **Nest Cam の TLS 1.0**：「state-of-the-art security tools」（収録の後の文書）と比べるか。
4. **取り出した映像・画像を報告や論文に載せてよいか**：人や実験室が写っている。
5. **外部への連絡**：データセットの作成者への問い合わせ、製造者への連絡をするか。

## 9. 確かめ方

外付けディスクを `~/datasets` にマウントしてから実行する。

```bash
# A：SmartCam の映像の接続（視聴者 129.94.5.83 のポート 48041）を取り出す
tshark -r ~/datasets/raw/unsw-iot-2018/benign/18-05-28.pcap \
  -Y 'tcp.port==48041 && ip.addr==129.94.5.83' -w smartcam-48041.pcap
tshark -r smartcam-48041.pcap -q -z follow,tcp,raw,0 > follow.txt
# RFC 4571 の枠をはずして H.264 と μ-law を取り出す（~/datasets/claims/dig/scripts/rtp_h264.py）
# A・C：カメラの ServerHello（tcp.srcport が 443 なら HTTPS、5222 なら XMPP）
tshark -r ~/datasets/raw/unsw-iot-2018/benign/18-05-28.pcap \
  -Y 'ip.dst==192.168.1.248 && tls.handshake.type==2' \
  -T fields -e frame.number -e ip.src -e tcp.srcport -e tls.handshake.ciphersuite

# B：SimCam の画像を取り出す
tshark -r ~/datasets/raw/cic-iot-2022/2021_11_02_Active.pcap \
  --export-objects http,simcam-obj -Y 'http.request.method=="PUT"'
# B：PUT の前後のイベントと通知（フレーム番号と時刻）
tshark -r ~/datasets/raw/cic-iot-2022/2021_11_02_Active.pcap \
  -Y 'ip.src==192.168.137.149 && http.request' \
  -T fields -e frame.number -e frame.time_utc -e http.host -e http.request.uri

# D：SNH-V6410PN のイベントの通知
tshark -r ~/datasets/raw/deakin-iot/pcapFull/2023-07-26.pcap \
  -Y 'http.request.uri contains "event.stw"' -T fields -e frame.number -e http.file_data
```

- 取り出した映像・画像・音声：`~/datasets/claims/dig/`（リポジトリの外）。
- 認証情報（トークン、署名、キー ID）の値：非公開のリポジトリ quarant-results の `claims/`。
- 集めた文書の本文：`~/datasets/claims/snapshots/`。
