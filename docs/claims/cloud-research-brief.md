# クラウドでの調査の指示：製造者の文書と先行研究

利用者が寝ている間に、クラウドのセッションで進める調査。**途中で質問しない**。分からないことは「未確認」と書いて次へ進む。

この環境には PCAP も、手元の外付けディスクもない。通信についての新しい事実は作らない。

## 製品ごとに調べること

### A. 製造者の文書

比較の基準は「収録（2018-03-20〜04-19）までに公開され、対象の機器に当てはまる説明」。

1. **読んだ版の本文を読み直す**。前後の文脈で、主張が何を指すか（機器とクラウド、アプリ、ウェブサイト、保存時）を確かめる。
2. **同じ URL の前後の版を確かめる**。`wb.py cdx` で一覧を取り、収録の直前の版、直後の版に同じ文があるか調べる。後継の URL（リダイレクト先、販売ページ、新しいプライバシー通知）も見る。
3. **日付を分ける**。公開日、改訂日、アーカイブの取得日を別々に書く。文書に日付がなければ「記載なし」と書く。
4. **適用範囲**。型番と世代が文書の対象に入るか。
5. 仕様書、データシート、マニュアル、サポート記事、公式 PDF、リリースノートを探す。

Ring と Hue では、2 と 4 で結論が変わった。Ring の「Encryption: Bank-grade」は 2017-11-15 以降の販売ページの仕様の欄になく、Hue の「using SSL」は 2017-09-24 以降の版になかった。**収録の時点で有効だったかを必ず確かめる**。

### B. 先行研究

論文、技術ブログ、CVE、脆弱性の報告を探し、**本文を読む**。検索結果の要約だけで読んだことにしない。

Hue では「平文の HTTP」と見えた通信の本文が、独自の層で AES で暗号化されていた（AV-TEST 2017 と一致）。**その製品の通信に別の暗号の層があるという報告がないか**を必ず探す。

### C. 書くもの

`docs/claims/research/<製品名>.md` に次を書く。

1. **判定の案**：「候補を維持」「未確認」「除外」のどれかと、理由を 1〜2 文。
2. **文書の表**：確認した文書（公開・改訂の日、アーカイブの日、書いてあること）、取得できなかった文書、探したが見つからなかった文書。
3. **先行研究の比較表**：資料名・著者・公開年・URL・ページか節／対象機器と調査時期／実際に観測・検証した内容／既存の解析と一致する点・異なる点／比較できない点と理由／判定（同一の既知問題、関連する別の問題、追加の知見になり得る、未確認）。
4. **手元の PCAP で確かめること**：版の境目、本文が暗号化されていないか、取得の通信のパスなど、次に手元で確かめる点を、ファイルやホストの手がかりとともに並べる。
5. **既知問題の再確認にとどまる点／追加検証する価値がある点／判断に不足する証拠**。

## 守ること

- **PCAP の事実は書かない**。通信の話は「既存の解析（claims.tsv）」と明記して引用する。先行研究の結論を、今回のデータの事実として扱わない。
- 確かめていないことは「未確認」と書く。読めなかった資料は、その旨と理由を書く。
- 同じ機種・世代・ファームウェアと確認できなければ、その違いか不明点を書く。
- ホスト名やポート番号だけから通信の目的を推測しない。
- 資料が見つからなかっただけで、新規とは判断しない。「初めて」と書かない。
- 引用は短くする（各資料で 1 文まで）。ページの全文をコミットしない。
- 認証情報などの秘密の値を書かない。
- `claims.tsv`、`handoff.md`、`results-yourthings.md`、`review-yourthings.md` は変えない。結果は `docs/claims/research/` にだけ書く。
- 日本語で、短く平易に書く。

## 進め方と終わり方

- 製品を 1 つ終えるごとにコミットして push する。途中で止まっても、それまでの分を残すため。
- ブランチは `claims-cloud-research`。
- 全部終えるか、これ以上進められなくなったら、`docs/claims/research/README.md` に製品ごとの判定の案の一覧と、できなかったことを書く。
- 最後に **`main` への PR を開く**。題は `Claims: cloud research`（通知はこの PR で届く）。**マージはしない**。
