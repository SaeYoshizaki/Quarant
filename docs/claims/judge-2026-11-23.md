# 自分の目で判定するための一覧（2026-11-23）

**同じ日に、利用者の調査の手順（6 つの区分、最も限定的な読み方）でやり直した結果は [reinvestigation/README.md](reinvestigation/README.md)。判定はそちらが新しい。**

これまでに見つけた「公式文書と通信の食い違い」の候補を、1 件ずつ判定できる形にまとめた。外付けディスクがなくても読めるように、文書の原文と Wayback のリンク、通信で見えたこと（ファイルとフレーム）を書き写してある。

- **判定の欄**：各項目の最後の「判定」に、次のどれかを書く。
  - **食い違い**：文書の言葉と通信が、読み方に頼らず違う
  - **弱い食い違い**：読み方によっては違う（範囲、時期、言葉のあいまいさ）
  - **言葉の上だけ**：暗号化はしているが、「最先端」「すべて」などの言葉と合わない
  - **外す**：比べる文書として不適、または食い違いとは言えない
- **★**：こちらの見立ての強さ（★★★ 強い、★★ 中くらい、★ 弱い）。参考なので、気にせず判定してよい。
- 文書のリンクはブラウザで開ける。通信の確認（tshark）はディスクが要る。認証情報の値は quarant-results の `claims/sweep-credentials.md`。
- 詳しい根拠：[report-2026-11-15.md](report-2026-11-15.md)（A〜E）、[blog-level.md](blog-level.md)（Eufy）、[compare-sweep.md](compare-sweep.md)、[results-yourthings.md](results-yourthings.md)、[pms.md](pms.md)、[sweep-results.md](sweep-results.md)、表は [claims.tsv](claims.tsv)。

## 1. Samsung SmartCam SNH-P6410BN（UNSW 2018）★★★

**文書**
> Security SSL ( AES 256bit )

- データシート（PDF の作成 2014-02-28）の仕様の表、[Wayback 2016-06-23](https://web.archive.org/web/20160623235657/https://www.samsung-security.com/SAMSUNG/upload/Product_Specifications/SNH-P6410BN_Datasheet.pdf)。収録の前。
- 同じ行がユーザーマニュアル p.33 にもある（[Wayback 2024-06-27](https://web.archive.org/web/20240627133604/https://www.wisenetlife.com/fileDownload.do?fileName=1491228809600.pdf&filePath=UPLOAD_MFGD_ATTRBT_PATH&downLoadName=User%20Manual-SNH-P6410BN-ENGLISH_Web-1113.pdf)）。

**通信**
- 機種はカメラ自身の UPnP の `modelName`（SNH-P6410BN、シリアル KHNL6V2H20003LX）。
- `18-05-28.pcap` フレーム 3194834〜3201825（2018-05-28 15:43 UTC、約 5.1 MB）：外の視聴者（129.94.5.83）へ、STUN のあと RTP で H.264 の映像（1920×1080）と G.711 の音声を**暗号化せずに**送った。取り出すと、絵も音もそのまま再生できた（実験室の机が写っている）。
- クラウドとの TLS は TLS 1.0。HTTPS はサーバーが AES-128 を選んだ。XMPP は AES-256（ここは一致）。

**引っかかる点**
- マニュアル p.22 に「Image encrypting」という**任意の設定**があり、画面の写真では初期値がオフ。利用者が入れていなかっただけ、とも読める。ただし仕様の「SSL (AES 256bit)」には条件が書いていない。
- 視聴者は UNSW の中のアドレス。大学の外を通ったかは分からない。

**先に書いた資料**：SmartCam の平文の映像は見つからず。Kaspersky（2018、ブログ）と CVE-2018-6295 は別の機種で経路を書いていない。Loi ほか（2017）は同じ研究室の機器を「平文ではない」としている（逆）。

**判定**：

## 3. Eufy HomeBase 2 とドアベル（CIC、2021-10）★★★

**文書**
> All recorded footage is encrypted on-device and sent straight to your phone—and only you have the key to decrypt and watch the footage. Data during transmission is encrypted.

- eufy の「Privacy Commitment」（カナダのストア）、[Wayback 2021-09-25](https://web.archive.org/web/20210925012802/https://ca.eufylife.com/pages/privacy-commitment)（収録の 18 日前）。

**通信**
- アプリで外から見た映像（`WAN_WATCH`、`WAN_RECORDING` の 4 本）：UDP の P2P で、Amazon のアドレスの中継を通る。
- 音声（AAC）は全部平文。そのまま 80 秒分を復号できた。例 `eufyhomebaseWANWATCH_1.pcap` フレーム 275 に ADTS の見出し `ff f1 60 40`。
- 映像（H.265）で暗号化されているのは、一部のフレームの先頭 128 バイトだけ（全体の最大 0.21%）。例 同じファイルのフレーム 213 に平文の開始コード `00 00 00 01 02 01`。

**引っかかる点**
- 報道（The Verge 2022）は「暗号化されていない」のはウェブポータルの映像だとし、Anker は「アプリの映像はずっと端から端まで暗号化」と答えた。論文（USENIX WOOT 2024）もアプリの映像を「暗号化」と書く。こちらの観測とは逆。
- 先頭 128 バイトを暗号化すれば普通には再生できないので、製造者はそれを「暗号化」と呼んでいるかもしれない。音声は全部平文。

**先に書いた資料**：同じ経路（アプリ）の平文の報告は見つからず。

**判定**：

## 5. Philips Hue Bridge（IoTraffic 2016-17、CIC 2021）★★

**文書（2016-17）**
> Philips Lighting, transfers data securely (using SSL) and will encrypt some data, such as your MAC address when it is stored.

- プライバシーポリシー、[Wayback 2017-03-30](https://web.archive.org/web/20170330130814/http://www2.meethue.com:80/en-au/privacy-policy/)（収録中）。この文は 2017-11 の改訂で消えた。

**文書（2021）**
> Hue only connects to the internet securely via a dedicated cloud so your devices cannot be seen from the open internet.

- FAQ、[Wayback 2021-12-22](https://web.archive.org/web/20211222052747/https://www.philips-hue.com/en-us/support/faq/hardware-and-connectivity)（収録中）。

**通信**
- 2016-17：通信の 70% が平文の HTTP。`dcp.cpp.philips.com:80` への POST の `Authorization: CBAuth`（ブリッジ ID と SSO トークン、4,810 回）、`bridge.meethue.com:80/queue/getmessage` の `auth`（8,370 回）（`PhilipsHue_0017882b9a25.pcap` フレーム 1586〜3925289）。
- 2021：通信の 27% が平文。`diagnostics.meethue.com/v2/diagnostics/report?...&sso=<トークン>`（4,760 回）、`dcp.dc1.philips.com:80` の CBAuth（1,017 回）。※ 2026-11-26 の確かめ直しで、要求の数は 246 回と 682 回と分かった（[05](reinvestigation/05-philips-hue-bridge.md)）。
- 2023-24（Passive-Mode-Study）も同じ形が続く。米国とフランスの別の個体で `sso` が同じ値。

**引っかかる点**
- 本文は別に AES で暗号化されている（AV-TEST 2017 は「十分に安全」と評価）。見えるのは見出しのトークンと ID。
- 2021 年の文の「dedicated cloud」（Philips のホストだけ）は一致。違うのは「securely」の部分だけ。

**先に書いた資料**：平文の HTTP は Mandalari ほか（PoPETs 2021、§5.5 p.379）と AV-TEST（2017）。文書との食い違いは見つからず。

**判定**：

## 7. VeraLite（YourThings、2018-03〜04）★★ 新しい候補

**文書**
> his username and an MD5 hash (security checksum) of the password, along with the serial number and hardware key, are sent to the remote access server using the https: (SSL encryption) protocol.
> NetworkMonitor runs on Vera and calls a php page on the remote access server using https, passing in the serial number and hardware key, …

- MiCasaVerde の wiki「Secure Remote Access TechInfo」、[Wayback 2016-10-13](https://web.archive.org/web/20161013232847/http://wiki.micasaverde.com:80/index.php/Secure_Remote_Access_TechInfo)（収録の前。ページの最後の編集は 2011 年）。

**通信**
- ハブは 13 日で 470 回、自分のログを**平文の FTP** で `82.77.228.112:21`（名乗り `mios-logs-service`、`MiOS LTD LOG SERVER 6`）に上げる。ユーザー名とパスワードは共通の値とみられる。
- `eth1-20180320.0840.1521553200` の 1 回分（21 ファイル）を組み立てた。`MiOSRestApi.log`（STOR フレーム 29838）に**ハードウェアキー（HWKey）が 4 回**、relay・device・account の 3 つのサーバーの**セッションキー**。`cmh-ra.log`、`sysinfo.log` にも relay のセッションキー。値は quarant-results。
- 機器自身は、同じキーを HTTPS（`vera-us-oem-authd11.mios.com`）で送っている。ログの中のコマンドの記録に入って、別の経路で平文で出ている。
- ほかにログには、LAN のカメラへのログインの試し（`http://192.168.0.30/check_user.cgi?user=test&pwd=test` など）、遠隔接続の SSH の設定。

**引っかかる点**
- 文書は遠隔接続の手順の説明で、ログの送信のことは書いていない。「キーを https で送る」が「キーをほかの方法では送らない」まで言っているか。
- wiki の本文は 2011 年の UI5 のころの説明。
- 確かめたのは 1 回分だけ（ほかの 469 回は未確認）。

**先に書いた資料**：ログを FTP で上げることは、利用者のフォーラムの投稿にある（ezlo community「Capturing Vera logs to my own FTP server instead of Vera」）。キーとセッションが入ることは見つからず。

**判定**：
