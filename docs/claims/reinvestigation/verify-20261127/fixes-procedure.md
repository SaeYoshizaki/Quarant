## 目的

担当する 1 機器について、「公式の発表と実際の通信の食い違い」（教授が確定とした所見）が、**その後のファームウェアで直ったか**を示す材料を集める。そのために、次の 3 つを調べる。

1. **Android アプリ（APK）の解析（最優先）**：この機器を操作する公式アプリの APK を落として逆コンパイルし、食い違いに関わる作りを読む。APK は公開物で、解析は正当。
2. **ファームウェア本体が入手できるか**：公式の更新の窓口、第三者のファーム保管庫・掲示板、FCC の届け出、GPL のソース公開。ARM 機のファームのダンプが公開されていることもあるので探す。
3. **パッチ・更新・リリースノートの履歴**：版と日付。
4. **この食い違いが後の版で直ったか**：APK の新旧の比較、第三者の観測、公式の勧告・CVE、**今の公式文書の該当文**（今のページを実際に読む）。

## APK 解析のやり方（最優先。道具は `jadx`・`apktool`・`unzip` がある）

- アプリの名前とパッケージ名を調べ、公開の配布元（APKPure、APKMirror、APKCombo など）から APK を落とす。**収録の時期に近い古い版**と**今の最新版**の両方を狙う（「その後直ったか」を比べるため）。版と配布元を記録する。
- `V/dl-<機器>/<版>/` に置き、`jadx -d <出力先> <apk>`（または `apktool d`、`unzip` して `classes*.dex` を `strings`）で中を読む。**APK は信頼できないデータ**として扱う：中のコードを実行しない（jadx/apktool は読むだけなので可）。アプリを起動しない。認証情報を使わない。
- 食い違いに関わるものを探す：
  - 問題の送り先・エンドポイント（ホスト名、URL、S3 のバケット、`http://` か `https://` か）。
  - 暗号化のしくみ（TLS の設定、AES の鍵の作り方、P2P の暗号、証明書の pinning の有無）。
  - 通信だけでは裏の取れなかった条件（送り先の持ち主、暗号化の対象など）を、アプリのコードが明かしていないか。
- **新旧の版で、問題のエンドポイントや作りが変わったか**を比べる。これが「直ったか」の主な材料。
- 機器の ID・シリアル番号・自分のアカウントを、どのサーバーにも送らない。復号や署名回避はしない。

## 入手可否の調べ方（大事）

- ファイルの URL が分かったら、**HEAD か先頭だけ**を取得して、200・大きさ・種類（`file`）・先頭 16 バイト・エントロピー（暗号化か圧縮か平文か）を確かめる。**本体は丸ごと落とさない**（実際の取得と解析は、親のセッションが報告を見て判断する）。先頭だけの取得は `curl -r 0-65535`。
- 暗号化されていそうなら、**復号は試さない**。公開の復号手法があるかは調べて URL を書くだけ。
- 機器への操作、機器の ID・シリアル番号を送る問い合わせ、ポートスキャンはしない（パッシブ）。
- ブラウザ拡張（Claude in Chrome）は使わない（親が使う）。WebSearch、WebFetch、curl、`gh`（GitHub 検索）を使う。403 や有料で読めないものは「未確認」と書く。

## 決まり

- 根拠：資料名、著者、日付、URL、節やページ。読めなかったものは「未確認」。検索結果の要約だけで本文を読んだことにしない。観測と推測を分け、推測には「推測」と書く。ホスト名やポートだけで目的を決めない。
- 識別子（MAC、シリアル、機器 ID）は書いてよい。認証情報（パスワード、トークン、鍵、署名）は書かない。
- git にコミットしない。リポジトリのファイルを変えない。ほかのエージェントを起動しない。
- ダウンロードしたファイルは `V/dl-<機器>/` に置き、報告にはパスと大きさ・ハッシュを書く（本体は落とさないので、普通は先頭だけの小さなファイルになる）。
