# 強い 5 件の確かめ直し（2026-11-27）

[一覧に戻る](../README.md)

[24 件の調べ直し](../README.md)で強かった 5 件（明確な矛盾の Sonos と Canary、条件付きの矛盾の SmartCam、SimCam、Eufy）を、**前の報告と判定を見ずに**、データと公式文書からもう一度組み立てた。論文の中心に使えるものを決めるため。

- 調べたのは「製造者が公式に発表していたことと、実際の通信が矛盾しているか」だけ。安全かどうかは評価していない。
- 手順は [procedure.md](procedure.md)（6 つの判定、最も限定的な読み方、収録の時点で有効だった文書、データ側と文書側の両方の証拠）。前の手順と同じで、「矛盾を否定する・弱める材料を探す」ことと、論文に要る項目（データセットの書誌・場所・期間、機種と版をどこから特定したか、文書の更新日と保存日）を足した。
- データは前と同じ公開データセットを、機器の MAC で切り出したもの（UNSW 2018 の 27 日、UNSW-IoTraffic の機器ごとのファイル、YourThings の 13 日、CIC IoT 2022 の攻撃以外の全ファイル）。
- 認証情報の値は非公開のリポジトリ `quarant-results` の `claims/verify-20261127.md`。取り出した画像・映像・音声と作業ファイルは外付けディスクの `~/datasets/claims/verify5-20261127/`（報告の中の `V/out/work-…` はここ）。

## 前の記録と違うところ

- **Canary 2016-17 を条件付きに下げた**：「All communication … is encrypted over TLS/SSL (HTTPS)」の FAQ は、2016-08-22 と 2018-08-18 の保存しかなく、収録の期間（2016-11〜2017-03）に載っていたか確かめられない。前は前後が同じ文なので有効とみなしていた。「当時も同じだったとは推定しない」の決まりに合わせた。
- **SmartCam を「記載なし」に下げた**：前は Hanwha の脆弱性の報告（2018-03-21）の「CVE-2018-6295 Unencrypted way of remote control and communications … Resolved」と比べて、ファームが 3 月以降なら矛盾とした。今回は、(1) この CVE がどの通信を指すかを報告も NVD も書いていない、(2) 元の Kaspersky の公表（2018-03-12）が平文として挙げたのは HTTP API と更新だけで、映像ではない、(3) この報告が 2018-05〜06 に公開されていたかも確かめられない（リンクのあるページの保存は 2018-08-20 から）、ので最も限定的な読みでは範囲の外とした。マニュアルの「Image encrypting」も、設定の状態と「image」が映像を含むかの両方が決められないので「記載なし」。平文のライブ映像（2016 年 9 回、2018 年 28 回、うち研究室の外の相手 22 回）そのものは確か。
- **SimCam の比べる文書を替えた**：前に中心に使った製品ページ（2020-08-08 の保存）は、2021-01-24 までに別の文に差し替わっていて、収録の時点で有効だったと言えない。今回は収録の 9 日前に保存された FAQ の「we never have access to your data」で判定した。

## 新しく分かったこと

- **Sonos**：平文の更新の確認 28 回のうち 15 回は、機器が毎日自分で送っていた（残りはデータセットの作成者のアプリの操作の直後）。操作のない日（04-16〜19）にもある。同じプライバシーの文書が、製造番号とソフトの版を「集めるデータ」と書いている。2021 年は収録地のカナダ版の文書も同じ暗号の文だった。
- **Canary**：平文の HTTP の送り先 `h.canaryis.com` は、Canary の社内の認証局で相互認証の TLS を受けるサーバー（`i.canaryis.com`）と同じ IP。収録期間中に保存されたドイツ語版の FAQ にも同じ文がある。ファイアウォールの公式記事は使うポートを TCP 443 と UDP 123 だけとしている。IEEE S&P 2019 の SoK（Alrawi ほか）は YourThings のデータで Canary を「完全に暗号化」と評価していた（YourThings の Canary にも平文の HEAD が 158 回ある。2026-11-07 の記録。tshark での確かめ直しは未）。UNSW の MUD の一覧には、この TCP 80 の通信が許可リストとして載っている（平文であることや公式の説明との食い違いは書いていない）。
- **SimCam**：人が写った画像の送信 16 回すべてに `x-amz-acl: public-read`（誰でも読める状態で置く指定）が付いていた。実際に公開だったかは、保存先にアクセスしていないので未確認。カメラに入っていた AWS の鍵の ID を公開の方法で手元で計算すると、保存先と同じアカウントになる（鍵は使っていない）。更新サーバーが返すファームの名前は Simshine の配布物と一致。一方、同じ時期のプライバシーポリシー（2021-10-06）と App Store の説明（2021-10-09）は、画像がサーバーを通ることと有料のクラウド保存を開示している。だから「隠していた」とは書けず、「FAQ の言い切りが、通信とも、同じ会社のほかの開示とも食い違う」までにとどめる。
- **Eufy**：ドアベル自身の製品ページに「AES data encryption ensures your footage is kept private on transmission」がある（米国 2021-07・10、カナダ 2021-12。米国版は 7 月の AES-256 が 10 月に AES-128 に書き換わった）。平文は H.265 の文法（フレームの番号の一致）でも確かめた。ただし、今の公式記事（日付なし）は「ライブ視聴中の手動の録画はスマホに保存」と書き、遠隔の録画の操作で送られたのは「録画した映像」ではない方に傾く。同じ機器の論文 Goeman ほか（USENIX WOOT 2024）を読んだ。画像の頭だけの暗号化は報告済み。2021 年のファームで映像の大部分と音声が中継に平文で出ていたことは、読んだ範囲では書かれていない。

## 判断待ち

- **Eufy の「footage」**：eufy 自身が eufyCam 2 のページ（2020-12）で「Live-stream and record footage」と書いている。同じ会社の言葉づかいで「footage」をライブの映像まで含めて読むなら、ライブ視聴の平文は条件なしの明確な矛盾になる。今の決まり（最も限定的な読み方）を変えることになるので、利用者が決める。
- **SmartCam の Kaspersky の公表**：本文は WebFetch の要約でしか読めていない（未確認）。CVE-2018-6295 が何を指すかの根拠なので、全文で確かめる。
