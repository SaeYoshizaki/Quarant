### E1-1：IoT-23（実マルウェア、フロー単位のラベル）

**集計**（検出器があるラベル種別を単位に数える）

- 検出：5 / 10。内訳は、Mirai と Hakai の C&C、Muhstik のスキャンとブルートフォース。
- 見逃し：5 / 10。
- 検出器なし：DDoS、FileDownload。
- 正常機器で振る舞いの WARNING：0 件。

**解釈と限界**

- ※1：Mirai の「PartOfAHorizontalPortScan」は、実際には**1 つの IP の 1 ポートへの 121 回の試行**で、多数の宛先を探す横方向のスキャンではない。ラベルの付け方の問題なので、Quarant の見逃しとして扱うのは適切ではない。
- ※2：ブルートフォースを専用に検出する機能はない。標的ごとの「執拗な接続試行」として表面化した。
- ※3：少量で低頻度の C&C は、通信の振る舞いだけではほぼ区別できない。
  - 例：Torii は 1 日に約 15 回、443 番で TLS 通信をしていた。
  - 脅威情報（IOC との照合）がないと検出は難しい。Phase 2 の脅威情報連携の根拠になる。
- **しきい値の決め方**：`PERSISTENT_CONNECTION_ATTEMPTS` のしきい値（30 回／時）は、UNSW の 1 日目（正常）の分布と、このシナリオ 8-1 を見て決めた。そのため、8-1 での検出は**評価データでの調整の結果**であり、汎化の根拠にはならない。
  - 汎化の確認として、UNSW の残り 19 日（正常）での誤検知を E1-2 で測った。
- **データの性質**：感染した機器は主に Raspberry Pi で、1 シナリオにつき 1 台。LAN 内の文脈はほとんどない。

### E1-2：UNSW IoT traces（正常、20 日、MAC の正解あり）

**対象**：2016-09-23〜10-12 の 20 日分の PCAP（圧縮時 6.4GB）と、正解の機器一覧（MAC と機器名、31 件）。

- **開発用**：16-09-23。しきい値の調整に使った。
- **ホールドアウト**：残りの 19 日。調整に使っていない検証用データ。

```bash
quarant analyze <day>.pcap --out runs/unsw-<day>/events.jsonl
quarant dataset-eval unsw --run runs/unsw-<day> --devices List_Of_Devices.txt
```

**機器識別**（20 日分を合算）

| 項目 | 結果 |
|---|---|
| 一覧の機器を 1 日以上観測できた | 31 / 31 |
| OUI からベンダーが分かった | 31 / 31。うち 7 台は、Wi-Fi モジュールや OEM の製造元で、製品ブランドとは異なる ※ |
| DHCP を観測できた | 31 / 31 |
| ホスト名が分かった（DHCP または mDNS） | 19 / 31 |
| mDNS を観測できた | 13 / 31 |
| SSDP を観測できた | 7 / 31 |

※ ブランドと OUI のベンダーが異なる例：

- iHome → AzureWave
- PIX-STAR → AMPAK
- Android → Murata
- Blipcare → Rezolt
- Insteon カメラ → TP-Link（OEM）
- 名前のない機器 → Reecam
- ノート PC → AzureWave

OUI から分かるのは「NIC の製造元」であり、製品ブランドとは限らない。Quarant が `mac_vendor` を `reference_match` として扱い、カテゴリの推定に直接使っていないのはこのため。

**正常データでの振る舞い検知**（ホールドアウト 19 日）

| 検出 | INFO | WARNING 以上 | 内容 |
|---|---|---|---|
| `PERIODIC_COMMUNICATION_OBSERVED` | 201 | 8 | WARNING の内訳：Galaxy Tab→北京の IP の 5222 番（XMPP、DNS なしの直接接続）が 6 件、ノート PC→IP 直指定の HTTP（毎時）が 2 件。悪性ではなく、設計どおりの「要確認」 |
| `PERSISTENT_CONNECTION_ATTEMPTS` | 150 | 4 | 無応答の宛先への再試行など。悪性ではない |
| `IP_MAC_BINDING_CHANGED` | — | 3 | ゲートウェイによる中継、ランダム化 MAC。機器構成による誤検知 |
| `LATERAL_SCAN_SUSPECTED` | — | 1 | **実際のスキャン**：MacBook（.243）が Insteon カメラ（.192）の 2.7 万以上のポートに、1 分間で接続を試みていた（ポート 1、2、3… の連番）。データセットではラベルが付いていないが、正しい検出 |

**解釈**

- 誤検知候補の WARNING は、19 日 × 31 台で 15 件だった（1 日あたり約 0.8 件）。
- INFO は「正常なテレメトリでも起こる観測」として出しており、これは設計どおり。
- 「正常」とされているデータの中にも、ラベルのない実際のスキャンが含まれていた。**正常データの誤検知率を測るときは、検出結果を人が確認する手順が欠かせない**。
- WARNING 以上の検出の大部分は、2016 年の機器による平文 HTTP と古い TLS（`INSECURE_HTTP` 30,086 件、`I7_TLS_WEAK_VERSION_OBSERVED` 4,515 件）。これは実在する弱点の観測であり、誤検知ではない。ただしイベントの冗長性が高く、相関によるまとめ（Phase 2）が必要。
- **性能**：
  - 1 日（約 15〜40 万フロー）あたり、20 秒〜2 分。
  - 当初は、接続先の多い機器がいる日に 21 分かかっていた。I5 照合をフローごとにやり直していたためで、キャッシュで解消した（同じ日で 128 秒、出力は同一）。

### E1-3：UNSW IoT attack traces（ARP スプーフィングなど、攻撃の時間窓の注釈あり）

**対象**：攻撃と正常通信を含む 5 日分の PCAP（2018-06-01、06-02、10-22、10-23、10-24。約 9.5GB）。

- 正解は、被害機器の MAC ごとの攻撃時間窓（開始と終了の Unix 時刻、攻撃名）。
- 18-10-24 のファイルは途中で切れていた。Quarant は読めた部分（約 5 時間）を解析し、警告を出した。

```bash
quarant analyze <day>.pcap --out runs/unswatk-<day>/events.jsonl
quarant dataset-eval unsw-attacks --run runs/unswatk-<day> --annotations annotations/   # 許容誤差 ±2 分
```

| 攻撃の種類 | キャプチャ内の時間窓 | 検出 | 備考 |
|---|---|---|---|
| ArpSpoof（1・10・100 pps、LAN 内の攻撃者） | 27 | **27（100%）** | レート別でも 9/9、9/9、9/9。検出は `IP_MAC_BINDING_CHANGED` |
| TcpSynDevice（SYN flood） | 36 | — | 検出器なし |
| TcpSynReflection | 36 | — | 検出器なし |
| UdpDevice（UDP flood） | 21 | — | 検出器なし |
| PingOfDeath | 15 | — | 検出器なし |
| Ssdp、Snmp、Smurf（リフレクション） | 12、6、9 | — | 検出器なし |

**誤検知の候補**：攻撃時間窓の外で、`IP_MAC_BINDING_CHANGED` が 107 件出た。

- そのほとんどは、正解の機器一覧にない MAC がゲートウェイ（.1）や機器（.175）の IP を名乗ったもの。該当する MAC は次の 3 つ。
  - `2c:27:d7`（OUI は Hewlett Packard）
  - `8c:85:90`（Apple）
  - `08:00:27`（VirtualBox の仮想 NIC）
- これらは攻撃側の機材と考えられる。ただし、注釈のない区間でも攻撃していたのか、正規の機器なのかは、データからは確認できない。そのため誤検知候補として扱う。

**解釈と限界**

- 機器自身がアドレスと MAC の対応を宣言する L2 の攻撃は、パッシブ観測と相性がよく、低いレートでも見逃さなかった。
- 量で押す攻撃（フラッド、リフレクション）は、検出器がないため評価していない。Phase 2 の候補。
  - これらは、宛先あたりのパケットレートや反射応答の比率を使えば、説明可能な方法で検出できる見込みがある。
- 攻撃は、ラボで動かした攻撃ツールによるもの。

## E2：TLS ClientHello パーサの差分ファジング（2026-10-17、測定装置の妥当性検証として補助的に実施）

**目的**：監視装置が読み取った内容（Quarant のパーサ）が、標準的な実装（Go `crypto/tls`）の解釈と一致するかを確かめる。食い違いがあると、誤検知や見逃しの原因になるだけでなく、すり抜け（evasion）にも使われ得る。

**方法**（`internal/parserdiff`。オフラインで、どの機器にも何も送らない）

```bash
go test ./internal/parserdiff -fuzz FuzzClientHelloDifferential -fuzztime 10m
quarant parser-diff --pcap <capture>
```

**分類**

| 分類 | 意味 |
|---|---|
| `agree` | 一致 |
| `quarant_only` | 比較相手が拒否する入力を、Quarant が ClientHello と判定した。存在しないものを報告し得る |
| `reference_only` | Quarant が正常な ClientHello を見落とした |
| `field_mismatch` | 両方とも受け入れたが、読み取った項目が食い違った |
| `lenient_unparsed_extension` | Quarant が中身を解釈しない拡張だけが不正。報告する項目は影響を受けないので許容する |
| `reference_lenient_rfc_invalid` | 比較相手が RFC 違反（セッション ID が 32 バイト超、暗号スイートが空など）を受け入れた。Quarant の拒否が正しい |

**ファジングで見つかり、修正した読み違い**（それぞれ回帰用のテスト入力として保存した）

1. 拡張ブロックが壊れていても、途中までの結果を正常として返していた。後ろにある `supported_versions` を読み落とすと、TLS 1.3 のクライアントが旧バージョンを使っているように見える。
2. データの途中にある 0x16 から ClientHello を探していた。TLS ではないデータから、存在しない ClientHello を作り出し得る。
3. 拡張ブロックの終わりと ClientHello の終わりが一致しているかを確認していなかった。圧縮方式が欠けた ClientHello も受け入れていた。
4. 中身が空の SNI 拡張を受け入れていた。SNI の構造の検証を `crypto/tls` と同じ厳しさにした。
5. （コードを読んで見つけたもの）失敗した候補位置で読み取った値が、結果に持ち越されていた。

**実データでの測定**

| データ | ClientHello | 一致（修正前／修正後） | 複数セグメントにまたがる | 届いた順と並べ直した順で結果が変わる | 解析対象外のポートで見落とし |
|---|---|---|---|---|---|
| UNSW 2016（16-10-11） | 2,792 | 100% ／ 100% | 0 | 0 | **102（3.7%）**。993、5228、80、56700、1119 番 |
| UNSW 2018（18-10-24） | 969 | 100% ／ 100% | 0 | 0 | **17（1.8%）** |
| 2026 年の実通信（手元の PCAP） | 87 | 100% ／ 100% | **86（99%）** | 0 | 0 |

**解釈**

- **ファジングで見つけた読み違い**：正常な機器の通信では起きなかった（修正前でも一致率 100%）。効果は、異常な入力や細工された入力への頑健さ、つまりパッシブ監視を欺かれにくくすることにあり、正常時の精度には効いていない。
- **ポート番号に頼った判定による見落とし**：実データでは 1.8〜3.7% あった。内容から TLS を判定するように変えた結果、UNSW の 1 日分で解析できた ClientHello は 2,693 件から 2,794 件に増え、弱い TLS の検出も新たに見つかった。
- **2026 年の通信**：ClientHello が複数の TCP セグメントにまたがるのが普通になっていた（量子耐性の鍵交換 X25519MLKEM768 で大きくなったため）。今回は並べ替えの影響はなかったが、TCP の再組み立てをしていないことは、現代の通信では危険が大きい。並べ替えや再送を起こした合成 PCAP で評価する必要がある（次の課題）。

## E2b：HTTP／MQTT パーサの差分検査と TCP の組み立て（2026-10-17、測定装置の妥当性検証の続き）

**目的**：E2 を HTTP と MQTT に広げる。あわせて、TCP の再送と並べ替えが検出に与える影響を測る（ROADMAP Step 1-4）。

**方法**（`internal/parserdiff`。オフラインで、どの機器にも何も送らない）

| 対象 | 比較相手 | 比べる項目 |
|---|---|---|
| HTTP リクエスト | Go `net/http.ReadRequest` | メソッド、パス、クエリ、バージョン、ルールが読むヘッダ（`authorization`、`cookie`、`host` など） |
| MQTT のクライアント通信 | mochi-mqtt のパケットデコーダ（MQTT 3.1／3.1.1／5、MIT ライセンス） | プロトコル、レベル、クライアント ID、ユーザー名、パスワード、トピック |

- **実行方法**：

  ```bash
  go test ./internal/parserdiff -run '^$' -fuzz FuzzHTTPRequestDifferential -fuzztime 10m
  go test ./internal/parserdiff -run '^$' -fuzz FuzzMQTTDifferential -fuzztime 10m
  quarant parser-diff --pcap <capture>   # TLS、HTTP、MQTT をまとめて出力
  ```

- **報告に含めないもの**：ヘッダの値と認証情報。食い違った項目の名前だけを出す。
- **許容する食い違い**：
  - 構造上の食い違い（フレーミング、ヘッダの終わり、フラグ）は修正の対象にした。
  - 次の 2 つは `quarant_lenient` に分類して許容した。比較相手は意味上の規則で拒否するが、そのバイト列がネットワークを流れた事実は変わらないためである。
    - HTTP：RFC 9112 の厳密な規則（ヘッダ名の文字種、ヘッダ名とコロンの間の空白など）。
    - MQTT：UTF-8 の検証、CONNECT のフラグの組み合わせ、v5 のプロパティの中身。
  - HTTP では、`LooksLikeHTTP` が知らないメソッドを `gated_method` として別に数える。HTTP でないデータを HTTP と誤認しないための、意図した制限である。

**見つかり、修正した読み違い**（それぞれ回帰テストあり）

1. **HTTP：本文をヘッダとして読む**：ヘッダが `\n\n` で終わり、本文に `\r\n\r\n` があると、本文の行をヘッダとして読んでいた。本文の文字列から、平文の `Authorization` ヘッダを作り出し得る。ヘッダの終わりを 1 行ずつ探す方式（`net/http` と同じ）に直した。
2. **HTTP：改行の混在**：`\n\r\n` のように改行が混在するリクエストで、ヘッダの終わりを見落としていた。
3. **HTTP：行の折り返し**：行頭が空白の継続行（RFC 9112 5.2 の obs-fold）を捨てていた。`Authorization:` の次の行に値を書くと、認証情報を空として読んでいた。`net/http` と同じく、前のヘッダの値につなげるようにした。
4. **MQTT 5 の will**：will を設定した CONNECT を読めなかった。will プロパティを読み飛ばしていなかったため。その結果、平文のユーザー名とパスワードを見落としていた。
5. **MQTT の固定ヘッダ**：フラグを検証していなかった。1883 番ポートに流れる意味のない 2 バイトでも、MQTT パケットと見なしていた。
6. **比較相手の不具合**（参考）：mochi-mqtt は、5 バイトの Remaining Length を受け入れる（値がオーバーフローする）。比較相手の側に、仕様の上限（4 バイト）を加えた。

**ファジング**：修正後、3 分ずつ実行した。HTTP は約 770 万回、MQTT は約 470 万回、TLS は約 2 万回（比較相手との TLS ハンドシェイクを擬似的に行うため遅い）で、許容しない食い違いは 0 件だった。

**実データでの測定**（`quarant parser-diff`）

| データ | HTTP（解析対象のポート） | 一致 | 解析対象外のポートの HTTP | 届いた順の連結が本来のバイト列と違う | MQTT |
|---|---|---|---|---|---|
| UNSW 2016（16-10-11） | 3,535 | 100% | **3,898（52%）** | 521（15%、すべて再送による重複） | 0 |
| UNSW 2018（18-10-22） | 2,976 | 100% | **14,303（83%）** | 676（23%） | 4（一致） |
| UNSW 2018（18-10-24） | 804 | 100% | **4,096（84%）** | 57（7%） | 1（一致） |
| IoT-23 Honeypot 5-1 | 157 | 100% | 0 | 0 | 0 |

- 解析対象外のポートの内訳：UPnP の制御と記述（49152〜49154、5000、2869）、Chromecast（8008）など。
- メソッドの内訳：GET が最も多い。次に UPnP のイベント通知（GENA の `NOTIFY`／`SUBSCRIBE`／`UNSUBSCRIBE`）で、18-10-22 では `NOTIFY` が 5,812 件あった。

**Quarant 本体の変更**（D18）

- 上記のパーサの修正（HTTP 3 件、MQTT 2 件）。
- 方向ごとに、シーケンス番号の順にバイト列を組み立てる（`analyzer/reassembly.go`）。
  - キャプチャ側の欠落は、受信側の ACK から判定して飛ばす。
  - フローのレコードに、`capture_gaps`／`capture_gap_bytes`／`retransmitted_bytes` を出力する。
  - 内容で TLS と判定する場合は、シーケンス番号がストリームの先頭に当たるセグメントで判定する。先頭より前に届いたセグメントは保留する。
- LAN 内の UPnP の通信（機器記述ファイルの取得、SOAP の制御、GENA）を、管理画面、管理 API、設定用の窓口のヒューリスティクスから外した。`/setup.xml` は WeMo の UPnP 機器記述ファイル。
- HTTP を内容で判定する範囲は広げなかった。LAN 内の HTTP は D17（要求と応答の組を使う検出だけ）で扱う。

**変更前後の比較**（main と比較。イベントの種類ごと）

| データ | イベント数（変更前 → 変更後） | 変化 |
|---|---|---|
| UNSW 16-10-11 | 14,704 → 14,642 | `INSECURE_HTTP_BODY_SECRET` −35 件。スマートフォン 1 台の推定イベント −27 件 |
| UNSW 18-10-22 | 15,142 → 15,147 | 平文の HTTP、URL 内のトークン、トークンが各 +2 件。`INSECURE_HTTP_BODY_SECRET` −1 件 |
| UNSW 18-10-24 | 3,339 → 3,339 | 変化なし |
| 2026 年の実通信 | 130 → 130 | 変化なし |
| 合成シナリオ | 8/8 検出、陰性対照の違反 0 件、WARNING 以上 78 件 | 変化なし |

すべての差について、原因を確かめた。

- **誤検知の解消**：`INSECURE_HTTP_BODY_SECRET` の減少（−36 件）。再送された GET が 2 回ぶん連結され、2 回目のヘッダ（`key=` を含む）を本文として読んでいた。
- **見落としの解消**：18-10-22 で増えた 6 件は、5 バイトが重なる部分的な再送があった 2 本のフロー。重複したバイトでリクエストが壊れて読めず、URL 内のトークンの平文送信を見落としていた。
- **再評価の機会の変化**：スマートフォン（192.168.1.208）の推定イベント（基準から外れた宛先など）の減少。減ったイベントは、すべて再送のあったフローで起きていた。変更前の版は、再送された重複バイトでバッファが増えるたびにルールを再評価し、その時点の機器のカテゴリでイベントを出していた。重複をきっかけにした再評価は意図した挙動ではないので、この減少は正しいと判断した。
- **TLS 関連の検出**：組み立て処理の不具合を 2 つ直したあとは、変更前と一致した。
  - キャプチャがサーバーの SYN/ACK から始まる場合。
  - 内容で TLS と判定した通信で、サーバーの最初のセグメントが逆順に届く場合。
- **処理時間**：CPU 時間は同等だった（18-10-24 で 24.9 秒 → 23.1 秒）。最大メモリは 58MB → 67MB に増えた。
- **E4 への影響**：E4 の集計スクリプトを、この 3 日分の変更前と変更後の解析結果に適用した。要件ごとの「証拠が現れた IoT 機器の数」は、すべて変わらなかった。

**解釈**

- **パーサの読み違い**：E2 の TLS と同じく、正常な通信では起きなかった（一致率 100%）。効果は、細工された入力への頑健さにある。
- **TCP の組み立て**：
  - 届いた順の連結は、HTTP のストリームの 7〜23% で、本来のバイト列と食い違っていた。
  - 検出への影響は、件数としては小さかった（1 日あたり数十件）。ただし、誤検知（再送されたヘッダを本文として読む）と見落とし（壊れたリクエスト）の両方向に効いていた。
  - 合成データでは、並べ替えだけで平文の Basic 認証の検出が消えることを確かめた。
- **ポート番号に頼った HTTP の判定**：影響は TLS（1.8〜3.7%）よりずっと大きかった。HTTP の 52〜84% が、既存の HTTP の検出の対象外だった。
  - 大半は、LAN 内の UPnP の通信（スマートフォンから機器への制御、機器のイベント通知）。
  - 外部への通信も含まれる。例えば WeMo は、MAC アドレスを含むパスで、ログファイルを平文の HTTP（8899 番ポート）でクラウドへアップロードしていた。
  - 試しにすべての HTTP ルールを適用すると、18-10-22 で次のようになった。
    - 平文のログのアップロードの検出：1 件 → 20 件。
    - 平文の HTTP の検出：3,828 件 → 22,198 件（大半が LAN 内の UPnP）。
  - この範囲を広げるかは未決定（STATUS の既知の問題 8）。

**限界**

- **MQTT の量**：実データの MQTT は 5 ストリームしかない。実データでの妥当性は、ほとんど確認できていない。
- **組み立て処理**：
  - SYN を観測しておらず、最初のセグメントが逆順に届いた通信は、まだ正しく組み立てられない。
  - 証拠のない欠落は、8 セグメント待ったあと飛ばす。
  - キャプチャ時の欠落の判定は、ペイロードを蓄積するフローだけで行う。
- **対象外の機能**：DHCP の差分検査は行っていない。DHCP のデコードは gopacket（`layers.DHCPv4`）が行い、Quarant はデコード済みのオプションを読むだけで、独自のパーサを持たないため。

## E3：ETSI TS 103 701 の試験ケースのパッシブ評価可能性（2026-10-17、RQ1）

**目的**：ETSI EN 303 645 の公式な適合性評価の仕様である ETSI TS 103 701 V2.1.1（2025-05）の全 131 試験ケースについて、厳密にパッシブな観測者が判定に到達できるかを分類する。分類の基準は自分たちで作らず、規格自身の区別（conceptual と functional、IXIT、機器の操作）から導いた（[assessment/RUBRIC_FINAL.md](assessment/RUBRIC_FINAL.md)）。

### 方法

1. **1 回目の分類**：3 つの範囲を分担して全件を分類した。担当者間のずれを受けて、基準を 2 回改訂した。
   - v2：判定の向き、仮定の明記を追加。
   - v2.1：IXIT の中身を仮定で補わない。
2. **独立した 2 回目の分類**：別の 3 人が、1 回目の結果を見ずに、整理し直した基準で全件を分類した。
3. **一致率の確認**：中程度にとどまった（後述）。食い違いの大半は、「製造者の公開文書を IXIT の代わりに読んでよいか」の解釈の違いだった。
4. **基準 v3**：観測者のモデルを 2 つに分けた。
   - **N**：通信の観測と、第三者の参照情報（暗号カタログ、CVE、プロトコル仕様）。
   - **ND**：N に加えて、製造者の公開文書。

   両方の担当者が、それぞれ相手の結果を見ずに付け直した。
5. **裁定**：モデル N に残った 20 件の食い違いは、Claude が原文の合否基準を読んで裁定した。裁定の原則は P-a〜P-e の 5 つ（[assessment/adjudication.json](assessment/adjudication.json)）。モデル ND は裁定せず、2 人の判断の幅として報告する。
6. **著作権への配慮**：規格の文章はリポジトリに含めない。両方の分類について、本文と 8 語以上一致する箇所がないことを機械的に確認した（見つかった 1 件は書き直した）。

```bash
python3 scripts/assessment/agreement.py docs/assessment/source/pass1 docs/assessment/source/pass2 docs/assessment/agreement.md
python3 scripts/assessment/finalize.py docs/assessment/source/pass1 docs/assessment/source/pass2 docs/assessment/adjudication.json docs/assessment
```

### 一致率（試験ケース 131 件、[assessment/agreement.md](assessment/agreement.md)）

| 段階 | 一致率 | Cohen の κ |
|---|---|---|
| 基準 v2（観測者が 1 種類） | 0.71 | 0.44〜0.47 |
| 基準 v3・モデル N | **0.85** | 0.52 |
| 基準 v3・モデル ND | 0.82 | 0.64 |

モデル N の κ が一致率のわりに低いのは、ほとんどのケースが「判定不能」に集まっていて、偶然の一致の期待値が高いため。

### 結果（要件 = 試験グループ 78 件、[assessment/ts103701-final.md](assessment/ts103701-final.md)）

**モデル N（通信の観測者。研究の中心）**

| | 要件数 |
|---|---|
| 合否とも判定できる | **0** |
| 不合格のみ示せる | **22** |
| 合格のみ示せる | 1（5.3-4A：利用者の操作なしに更新が入ることの観測） |
| 判定できない | **55（71%）** |
| 判定できないが、規格の手順の外で手がかりは観測できる | 39 |

**モデル ND（通信＋製造者の公開文書）**：何らかの判定に到達できる要件は 32〜54（2 人の判断の幅）。公開文書を足すと判定できる範囲は広がるが、それは通信の観測ではなく文書の審査による。

### 解釈

- **適合は示せない**：通信の観測だけでは、ETSI の要件のどれについても「適合している」とは示せない。示せるのは違反の証拠（22 件）だけ。「未検出は安全の証明ではない」ことを、公式の評価仕様に照らして定量的に示した結果になる。
- **手順と観測のずれ**：判定できない 55 件のうち 39 件では、関係する手がかり（更新の通信、応答するサービス、バナーでのバージョン露出など）は観測できる。規格の評価手順は製造者の文書との照合を前提にしているので、パッシブな証拠を判定に使う道がない。
- **合否とも判定できる要件**：v2 では 3 件あったが、どれも製造者の公開文書によるもので、モデル N ではなくなった。

### 限界

- 分類も裁定も言語モデル（Claude と、その分担者）が行った。人による確認は、SaeYoshizaki による 10 件の抜き取りのみで、10 件すべてに納得を得た（[assessment/human-review.md](assessment/human-review.md)）。
- 裁定は 1 人（Claude）が行った。
- この分類が示すのは**理論上の**到達可能性。実際の通信でどれだけ証拠が現れるかは RQ2（E4 以降）で測る。例えば初期パスワード（5.1-1）は理論上「違反だけ示せる」だが、平文で流れて既定値と一致する場合に限られるので、現代の通信ではほぼ現れないと見込まれる。
- モデル N の κ は 0.52（中程度）。結果の数字は、裁定の原則を前提とした値として扱う。

## E4：違反の証拠が実際の通信に現れる率と、その精度（2026-10-17、RQ2）

**目的**：E3 でモデル N の観測者が「違反を示せる」とした要件について、次の 2 点を確かめる。

- 実際の IoT の通信に、その証拠がどれだけ現れるか（理論上の到達可能性と、実際に到達した割合の差）。
- Quarant の対応する検出が、違反の証拠として正しいか（精度）。

**方法**

- 要件と Quarant の検出の対応表を作った（[assessment/evidence-map.json](assessment/evidence-map.json)）。対応する検出がない要件は「未実装」として明示した。
- 現在の Quarant で、全データセットを解析し直した（UNSW 2016 を 20 日、UNSW 攻撃データ 2018 を 6 日、IoT-23 を 8 シナリオ、2026 年のノート PC の通信）。
- 検出の種類ごとにイベントを抜き取り、違反の証拠として正しいかを判定した（[assessment/precision-audit.md](assessment/precision-audit.md)）。その結果に合わせて、対応表の条件を絞り込んだ。
- 集計は機器単位で行った（MAC で数え、IoT ではない機器は除外した）。

```bash
python3 scripts/assessment/evidence_rates.py docs/assessment/evidence-map.json <runs> docs/assessment/evidence-rates.md <samples.json> docs/assessment/non-iot-macs.txt
```

**結果**（[assessment/evidence-rates.md](assessment/evidence-rates.md)。値は、証拠が現れた IoT 機器の数と割合）

| 要件 | 状態 | UNSW 2016（25 台） | UNSW 2018（32 台） | IoT-23（18 台） |
|---|---|---|---|---|
| 5.5-1／5.1-3 古い TLS（暗号のベストプラクティス違反） | 実装済み・精度 15/15 | **12（48%）** | **13（41%）** | 0 |
| 5.5-6 機密情報の平文送信 | 実装済み・精度 19/19（Cookie を除く） | 4（16%） | 2（6%） | 1（6%） |

| 5.1-2A 機器同士のパスワード認証 | 実装済み（絞り込み後は未監査） | 1（4%） | 1（3%） | 0 |
| 5.1-1／5.1-2 初期パスワード（候補） | 候補止まり（値の照合なし） | 2（8%） | 1（3%） | 0 |

| 5.9-3 秩序のない再接続（候補） | 候補止まり・精度 0 | 1 | 0 | 3（マルウェア） |
| 未実装の 9 要件 | — | — | — | — |

- 2026 年の通信は IoT 機器ではない（ノート PC 1 台）ので、年代比較には使えない。最近の IoT 機器のデータ（CIC IoT 2022）が必要。

**解釈**

- **理論と実際の差**：モデル N で違反を示せる要件は 23 件あるが、精度を確かめた検出で実際に証拠が出たのは 5 件（5.5-1、5.1-3、5.5-6、5.5-7、5.8-1）だった。残りは、次のどれかにあたる。
  - 未実装（9 件）
  - 候補止まりで違反を確定できない（初期パスワード、更新の暗号など）
  - 証拠と見えたものが、規格上は違反ではない（5.6-2）、または別の現象だった（5.9-3）
- **実際によく現れる証拠**：古い TLS（2016 年の IoT 機器の約半数）。次いで機密情報の平文送信（1 割前後）。
- **見かけの証拠と規格上の違反のずれ**：
  - **5.6-2**：検出したバージョン文字列は、プロトコルが公開を義務づけているものだった。
  - **5.9-3**：再接続ループは、設計の問題ではなく感染の振る舞いだった。

  パッシブな観測で「違反らしく見えるもの」と、規格上の違反との間には距離がある。この距離自体が RQ2 の結果になる。

**限界**

- 精度の監査は抜き取りで、判定は 1 人（Claude）。
- 最近の IoT 機器のデータがないため、暗号化の普及による変化（RQ3）は、まだ測れていない。
- 「候補止まり」の行は、違反の件数ではなく上限として扱う。

## E5：未実装だった 2 要件の検出を加えた（2026-10-17、RQ2）

**目的**：E4 で未実装だった要件のうち、実データに証拠が現れそうな 2 つについて、パッシブな検出を加える。それで出現率が変わるかを確かめる。

- **5.5-4**（認証なしで機器の機能にアクセスできる）：`I3_UNAUTHENTICATED_DEVICE_CONTROL`
- **5.12-1**（安全でない初期設定。ここでは UPnP によるポートの開放）：`I9_UPNP_PORT_MAPPING_REQUESTED`

どちらも、要求とその応答の組で判断する（D17）。実装の前に、使い捨てのツールで UNSW 2018 の LAN 内の HTTP を調べた。その結果、WeMo の SOAP 操作、Belkin NetCam のポート開放、ゲートウェイの IGD を確認した。

**結果**（[assessment/evidence-rates.md](assessment/evidence-rates.md)）

| 要件 | UNSW 2016（25 台） | UNSW 2018（32 台） | IoT-23（18 台） |
|---|---|---|---|
| 5.5-4 | 1（HP のプリンター） | 1（WeMo） | 0 |
| 5.12-1（候補） | 0 | 1（NetCam） | 0 |

- 証拠を示せる要件は 5 件から 6 件になった（5.5-4 を追加）。5.12-1 は候補止まり。
- 既存の検出の結果は変わっていない（[precision-audit.md](assessment/precision-audit.md) の E5 の節）。

**解釈**

- **5.5-4**：違反に見えるものの多くが、規格が認める例外と重なっていた。
  - ゲートウェイの IGD は、仕様上、認証を持たない。
  - プリンターの印刷は、家庭内に限ったサービスにあたる。
  - 例外にあたらない、はっきりした証拠は 2 台だけだった（WeMo の制御と、プリンターの設定の書き換え）。
  - E4 の 5.6-2（プロトコルが公開を求めるバージョン文字列）と同じ形の結果である。
- **5.12-1**：ポートの開放そのものは、通信から確実に観測できる。しかし、それが初期設定なのか、利用者が選んだのかは分からない。観測できる事実と、要件が問うことが食い違う例である。

## E6：2022 年の機器の起動時の通信（CIC IoT 2022 の 1-Power、2026-10-17、RQ3 の予備）

**目的**：最近の機器で、違反の証拠がどれだけ現れるかを見る。2016・2018 年の機器と比べる。

**方法**
- CIC IoT 2022 の 1-Power（40 台、電源を入れた直後の通信を 3 回ずつ）を、E5 と同じ Quarant（eef6bb7）で解析した。
- 集計は E4・E5 と同じスクリプトで行った。ゲートウェイは除外した。
- 証拠が出た機器は、すべて中身を確認した。

**結果**（実装済みの要件。[assessment/evidence-rates.md](assessment/evidence-rates.md)）

| 要件 | UNSW 2016（25 台） | UNSW 2018（32 台） | CIC 2022 の起動時（40 台） |
|---|---|---|---|
| 5.5-1／5.1-3 古い TLS | 12（48%） | 13（41%） | **4（10%）**：Echo Spot、Nest のカメラ、Netatmo のカメラ、Hue |
| 5.5-6 機密情報の平文送信 | 4（16%） | 2（6%） | 2（5%）：Hue、Home Eye のカメラ |
| 5.5-7 同上（外部への送信） | 3（12%） | 2（6%） | 2（5%） |
| 5.5-4 認証なしの操作 | 1 | 1 | 0（Sonos の DLNA の 1 件は、規格の例外） |
| 5.8-1 個人データの平文送信 | 1 | 1 | 0 |

- 古い TLS の 4 台は、原因が 2 種類に分かれた。
  - **機器側**（3 台：Nest のカメラ、Netatmo のカメラ、Hue）：ClientHello の版が TLS 1.0 で、対応版の拡張もなかった。つまり、機器自身が TLS 1.0 までしか提示していなかった。
  - **サーバー側**（1 台：Echo Spot）：機器は TLS 1.2 を提示したが、動画サービスのサーバーが TLS 1.0 を選んだ。
- 精度の確認で見つかったこと：5.5-4 の唯一の一致は、パソコンから Sonos への DLNA の問い合わせ（`GetProtocolInfo`）だった。EN 303 645 は 5.5-4 の本文で、DLNA を「家庭内に限って認証なしで提供してよい」例として挙げている。そこで、DLNA／UPnP AV のサービスを 5.5-4 の集計から除外した。

**限界**
- 起動直後の数分間だけの通信で、UNSW のような終日の通信ではない。起動後にしか接続しない宛先は見えないので、出現率は低めに出る可能性がある。
- 待機時（2-Idle）と操作時（3-Interactions）の解析で、同じ条件の比較をする。

## S2：既存ツール（Zeek、Suricata）との比較（2026-10-17、ROADMAP Step 2、RQ3）

**目的**：同じ PCAP を Quarant、Zeek、Suricata で解析し、次の 2 点を比べる。

- 攻撃や感染を検出できるか。正常な通信でどれだけ警告を出すか。
- ETSI EN 303 645 の要件の証拠（E4、E5 で Quarant が出したもの）を、既存ツールの出力からも得られるか。

**方法**（[scripts/step2/](../scripts/step2/)、結果の表は [assessment/tool-comparison.md](assessment/tool-comparison.md)）

- **使ったツール**：
  - Quarant（`b09c168`）
  - Zeek 9.0.0：同梱の `site/local.zeek` から、外部へ問い合わせる `detect-MHR` を外した設定
  - Suricata 8.0.7：ET Open（2026-10-17 に取得。有効なルール 53,211 件）
  - 3 つとも、既定の設定から変えていない。
- **データ**：
  - UNSW 2018 の攻撃データ 6 日分（攻撃の時間帯 165 件）
  - IoT-23 の 8 シナリオ
  - UNSW 2016 の正常データ 3 日分（16-09-25、16-09-27、16-10-11）
- **警告の分類**：攻撃・振る舞い系だけを、検出の比較に使った。設定上の問題を示す警告（平文、TLS、証明書）や、情報系の警告は、攻撃ではないため。
  - Quarant：スキャンの疑い、執拗な接続試行、周期通信、IP と MAC の対応の変化。
  - Suricata：ET のルールのうち、INFO、POLICY、CHAT、P2P、DNS、DYN_DNS、FILE_SHARING、GAMES、TOR 以外。Suricata エンジン自体の内部イベント（`SURICATA ...`）は別に数えた。
  - Zeek：notice のうち、`SSL::`、`Software::`、`CaptureLoss::` 以外。
- **検出の判定**：攻撃の時間帯（前後 2 分を含む）に、被害を受けた機器の IP アドレスが送信元か宛先になっている警告があれば、検出とした。3 つのツールで同じ基準を使った。
  - この基準は緩いので、同じ機器の 1 時間前の同じ長さの時間帯で同じ判定をし、偶然の一致率も求めた。
- **機器の数え方**：3 つのツールとも、Quarant の機器一覧の MAC アドレスで数えた。IoT ではない機器は除外した。

**解釈**

- **攻撃の検出は補い合う関係**：
  - Quarant だけが ARP スプーフィングを検出した（27/27）。Zeek と Suricata は、標準の構成では ARP の異常を警告しない。
  - Suricata だけが、反射攻撃（SSDP、SNMP）と、マルウェアの種類（Muhstik）を特定した。Quarant には、UDP のフローとシグネチャ照合がない。
  - Zeek の標準の構成では、攻撃系の通知は SSH の総当たりの 1 件だけだった。Zeek 9 に同梱のスクリプトには、スキャン検知がない。
- **フラッド系の攻撃は、どのツールも検出しなかった**：TCP SYN、UDP、Ping、Smurf の 119 件。ROADMAP Step 2 で「フラッド系の検出器を自作するかは、この結果を見て決める」としていた点について、既存ツールでは補えないことが分かった（自作するかは未決定）。
- **ETSI の要件の証拠**：
  - **古い TLS（5.5-1）**：Zeek と Suricata のログにも、まったく同じ機器が記録されていた。ただし、警告にはならない。古い TLS を要件の違反として解釈し、根拠（observed）と限界を付けて出すのは、Quarant だけだった。
  - **平文の機密情報、個人データ、認証なしの操作、UPnP のポート割り当て（5.5-6、5.8-1、5.5-4、5.12-1）**：既存ツールの標準の出力からは、得られなかった。
  - **バージョンの公開（5.6-2）**：Zeek の `software.log` の方が多くの機器を捉えた（主に HTTP の User-Agent）。どちらも候補止まりである点は同じ（E4 の精度監査で 0/22）。
- **正常データでの警告**：
  - 攻撃系の警告では、Quarant と Zeek は 0 件、Suricata は時期のずれた評判リストによるものだけだった。
  - 警告の総数は、Quarant がずっと多い（1 日あたり 1,579〜4,726 件）。設定上の問題をフローごとに出すためで、STATUS の既知の問題 1（イベントの冗長性）に当たる。
  - **追記（D19 の要約）**：`findings.json` で機器 × 状態にまとめると、同じ 3 日分の IoT 機器では、1 日あたり次のようになった（`quarant findings`）。
    - 状態：49〜54 件（15〜16 台）。
    - うち、ほかのイベントから導いた複合リスクを除くと：44〜48 件。
    - 最も多い状態：未登録の機器（1 台に 1 件）、古い TLS、弱い暗号の提示、平文の HTTP。
    - Suricata と Zeek の件数は、警告の数（通信ごとに出る）である。Quarant の状態の数とは単位が違うので、そのまま比べられない点に注意。

  | データ | イベント | finding（機器 × 種類） | condition（機器 × 状態） |
  |---|---|---|---|
  | UNSW 16-10-11（全機器） | 8,835 | 125 | 98（19 台） |
  | UNSW 18-06-01（全機器） | 34,334 | 84 | 73（22 台） |
  | IoT-23 3-1 | 81 | 5 | 5（2 台） |

**限界**

- **ツールの設定**：3 つのツールとも既定の設定で、運用で調整した状態ではない。
  - Zeek には、追加のパッケージ（スキャン検知など）を入れていない。
  - Suricata には、有料のルール（ET Pro）を使っていない。
- **データ**：
  - 2016〜2019 年の通信だけで、最近の機器の通信（CIC IoT 2022）では比べていない。
  - 正常データは 3 日分だけ。
- **検出の判定**：被害を受けた機器が関わる警告なら何でも数えたので、攻撃の種類と警告の内容の対応は、上の「どのツールの、どの警告で検出したか」で目で確かめた。
- **証拠の対応づけ**：Zeek と Suricata について、ETSI の要件への対応づけ（どのログの、どの項目を証拠と見なすか）は、この実験のために定めた。各ツールの開発者が意図した使い方とは限らない。
